## 1. 这一步在验什么

**验的是「引用可溯源」这条链能否走通，不是准确率达标。** P0-6 是可行性验证，不是评测。

链条有四个环节，任一环断裂则 §8 的检索路径需要重做：

```
① Dify 检索 API 能否按元数据过滤        →  断则四维过滤落不了地
② 召回的 chunk 是否包含答案所需事实      →  断则切块策略错
③ 返回的元数据能否定位回原文具体位置      →  断则引用无法构造（宪法第九条）
④ 答案中的事实能否对应到引用 chunk       →  断则「引用准确率」不可度量
```

环节 ③ 是宪法第九条的直接要求；环节 ④ 是 RAG 评审指出的缺口——**③ 只保证「引用指向真实 segment」，保证不了「引用与答案内容一致」**。

## 2. 测试语料

**唯一文档**：`corpus/06-色差与等级判定标准.md`（QC-STD-006 v3.2）

选它是因为它是 8 份规划文档中最难的一份，同时具备四个致命特征：

| 特征 | 为什么难 |
|---|---|
| **三 BU 混编** | §2 印染、§3 建陶瓷砖、§4 卫浴洁具，`bu_code` 只能标 `ALL`——RAG 评审指出的「文档级过滤在此失效」正是这里 |
| **三个同名阈值表格** | 都是「优等品/一等品/合格品」三档，且**卫浴表的首列是白度而非 ΔE**，草率作答会把「≥ 82」当成 ΔE 阈值 |
| **例外条款内嵌** | 例外与主条款在同一小节，测切块是否把它们切散 |
| **同名指标不同值** | 优等品判据：印染 ΔE ≤1.0 · 建陶瓷砖 ΔE ≤0.8 · 卫浴洁具 **白度 W ≥82**（主指标都换了） |

用简单文档问简单问题，100% 通过说明不了任何事。

## 3. 五个问题及其冻结判据

每题核对三层，**三层全过才算该题通过**：

- **(a) 检索层**：召回的 chunk 中确实包含回答所需的事实
- **(b) 定位层**：引用的 `document_name` / `segment_id` 能反查到原文的具体位置
- **(c) 一致层**：答案中每个关键事实（数值、阈值、条款）都能在引用 chunk 原文中逐字或语义等价找到

### Q1 · 单跳事实（基础能力）

> 印染事业部优等品的 ΔE 阈值是多少？

| 层 | 通过判据 |
|---|---|
| (a) | 召回 chunk 含 §2.1 的阈值表格或其等价文本 |
| (b) | 引用能定位到 §2.1 |
| (c) | 答案给出 **≤ 1.0**，且该值出现在引用 chunk 中 |

**失败信号**：答成 0.8（建陶的值）→ 表格混淆；答对但引用指向 §3.1 → 引用与答案不一致（(c) 不通过）。

### Q2 · 跨 BU 歧义（三选一）

> 优等品怎么判定？

**未指明事业部，而三个 BU 的判据互不相同，且卫浴的主指标是白度而非 ΔE。**

| 层 | 通过判据 |
|---|---|
| (a) | 召回覆盖 §2.1 / §3.1 / §4.1 中至少两节，或系统主动追问 |
| (b) | 若作答，引用须指向所答及的每一节 |
| (c) | **答案必须区分事业部**，或**主动追问是哪个事业部** |

**失败信号**：只给一个数值而不说明是哪个事业部；或把卫浴的白度 82 当作 ΔE 阈值报出。

### Q3 · 例外条款（切块质量）

> 印染优等品的色差阈值有没有不适用的情况？

| 层 | 通过判据 |
|---|---|
| (a) | 召回 chunk 含 §2.1 的「例外情形」段 |
| (b) | 引用定位到 §2.1 |
| (c) | 答案提到**深色系（L\* < 30）放宽至 1.5**，且提到**「色差从严」标注的批次不适用该放宽** |

**失败信号**：只答放宽、漏掉「不适用」的二次例外 → 例外条款被切散。

### Q4 · 表格取值（表格可检索性）

> 建陶一等品的平整度偏差上限是多少？

| 层 | 通过判据 |
|---|---|
| (a) | 召回 chunk 含 §3.1 表格 |
| (b) | 引用定位到 §3.1 |
| (c) | 答案给出 **≤ 0.5 mm/m**，且该值出现在引用 chunk 中 |

**失败信号**：答不出或答成印染的色牢度值 → 表格切块后语义丢失。

### Q5 · 无答案拒答（幻觉检测）

> 产品包装破损应该怎么索赔？

**文档中不存在该内容**（仅 §5 提及色差异议，与包装破损无关）。

| 层 | 通过判据 |
|---|---|
| (c) | 明确说明文档中未涵盖该内容，**不得编造赔偿流程或金额** |

**失败信号**：编造索赔条款，或强行引用 §5 争议处理充数。

| 结论 | 判据 | 后果 |
|---|---|---|
| 🔴 **不可行** | 环节 ③ 断裂——返回的元数据不足以定位回原文 | **§8 检索路径重做**，P3 的 2.0 人天作废 |

**Q2 的否决权已于 2026-08-30 评审后下调**，改为：

> Q2 失败 → **必须执行 §7 的机制⑤（按 BU 拆文件）**，并在 P3 补齐机制①②③；不单独把整体结论压到 🟡。

**下调理由**：Q2 测的是「消歧机制①②③⑤全都不存在时的裸检索表现」，而真实系统里这四层都在。Q2 失败**不代表**上线后会串答，它只说明「最后一道防线单独扛不住」——而它本来就不该单独扛。保留一票否决会因为一个不真实的最坏情况而误判整体可行性。

## 7. 跨 BU 消歧的机制设计（评审产出）

歧义不应靠「检测出来再追问」解决——那是最后一道。设计目标是**让它大部分情况下不产生**。

| 层 | 机制 | 覆盖 | 性质 |
|---|---|---|---|
| **①** | **身份注入**：用户身份带 `default_bu`，服务端在检索时强制注入 `bu_code IN (用户BU, 'ALL')` | 80%+ | **歧义不产生** |
| **②** | **实体推断**：产品词自动定 BU——「缸差/坯布/色牢度/门幅/克重」→ BU-A；「窑批/岩板/平整度/吸水率」→ BU-B；「白度/釉面/针孔/配套件/注浆批」→ BU-C | 大部分剩余 | 零成本，复用 §9.2 的 L1 规则表 |
| **③** | **会话粘性**：跨 BU 用户（如集团质量部）首轮追问一次，写入 session，后续不再问，直到显式切换 | 跨 BU 用户 | 只付一次成本 |
| **④** | **召回校验**：前三层未定 BU 且召回 top-k 出现 ≥2 个不同 `bu_code` → 不作答，转追问 | 兜底 | 可机械判定 |
| **⑤** | **按 BU 拆文件**（治本） | 根因 | 成本≈0 |
| **⑥** | **答案强制标注**：凡涉及 BU 特有数值必须写明适用事业部 | 最后一道 | prompt 约束 |

**机制① 是主力，且有安全含义**：过滤器必须由**服务端按用户身份注入，不接受模型或前端传入**。若由模型依据用户措辞填充，它既不构成权限控制（用户说「查建陶的」即越权），又成为 prompt injection 的靶点——这是宪法第十条的直接要求。

**机制⑤ 是治本的那条**：Dify 的元数据过滤最小单位是**整份文档**，segment 层不过滤。混编文档的 `bu_code` 只能标 `ALL`，过滤在此彻底失效。拆分方案：

```
06-色差判定-通用.md    bu_code=ALL    §1 测量基准 · §5 追溯 · §6 争议处理
06a-色差判定-印染.md   bu_code=BU-A   §2 全部
06b-色差判定-建陶.md   bu_code=BU-B   §3 全部
06c-色差判定-卫浴.md   bu_code=BU-C   §4 全部
```

内容本来就要写，只是分成四个文件——**成本接近零，但让 `bu_code` 过滤真正生效**。

**本轮刻意不拆**：保留混编状态是为了取得「混编文档到底有多糟」的基线数据。该基线是判断机制⑤ 收益的唯一依据，拆完就测不到了。

## 8. 执行结果（2026-08-30）

> 上方判据在执行前已 commit（`06febad` / `5571731`），执行后未作任何修改。

### 8.1 结论：✅ 可行

四个环节全部通过，五题三层全过。**按现设计推进，§8 检索路径无需重做。**

| 环节 | 结论 | 证据 |
|---|---|---|
| ① 元数据过滤能否用 | ✅ **强证据** | 见 §8.2 |
| ② 召回是否含答案事实 | ✅ | 五题 top-1 均命中目标小节 |
| ③ 元数据能否定位回原文 | ✅ | 返回 `document_name` + `segment_id`，且父块 content 首行即章节号（如「2.1 等级阈值」） |
| ④ 答案事实能否对应引用 | ✅ | 五题的引用标注全部正确，无一处指向错误 chunk |

### 8.2 元数据过滤：兑现此前的驳回

此前依据源码 `RetrievalModel.metadata_filtering_conditions` 驳回了 RAG 评审「Dify `/retrieve` 不支持元数据过滤」的结论，但**只查源码未实跑**。本次补齐实测：

给文档打上 `bu_code=ALL` 后，同一查询「优等品怎么判定？」在三种条件下：

| 过滤条件 | 召回 | 预期 | |
|---|---|---|---|
| 不过滤 | 3 条 | >0 | ✅ |
| `bu_code = ALL` | 3 条 | >0（文档标的就是 ALL） | ✅ |
| `bu_code = BU-A` | **0 条** | 0（文档不是 BU-A） | ✅ |

**三种条件行为全部正确 —— 过滤真实生效，不是被忽略。** 该驳回现有实测支撑。

同时确认：元数据字段需先经 `POST /datasets/{id}/metadata` 创建，再经 `POST /datasets/{id}/documents/metadata` 绑定到文档。这是 P3 建库流程必须包含的一步。

### 8.3 逐题结果

| | 判据 | 结果 |
|---|---|---|
| **Q1** 单跳事实 | 答出 ΔE ≤ 1.0 且值在引用 chunk 中 | ✅ 答对，并额外答出深色系放宽 1.5 与「色差从严」不适用，全部标 [1] 且确在同一 chunk |
| **Q2** 跨 BU 歧义 | 必须区分事业部或主动追问 | ✅ **三个事业部分别列出**，引用编号各自对应；未把卫浴白度 82 误作 ΔE |
| **Q3** 例外条款 | 须答出放宽 1.5 **且** 「色差从严」不适用 | ✅ 两层都答出——证明例外与主条款留在同一父块 |
| **Q4** 表格取值 | 答出 ≤ 0.5 mm/m | ✅ 答对且引用指向 §3.1 |
| **Q5** 无答案拒答 | 明确说明未涵盖，不编造 | ✅ 「所提供资料中未涵盖该内容」，并说明召回的三块各是什么，未强行充数 |

**Q2 的表现超出预期。** 冻结判据时我预计它最可能失败——三个 BU、判据结构还不同（卫浴主指标是白度而非 ΔE）。实际检索层三节全召回（0.6630 / 0.5792 / 0.5547），生成层正确区分。**Q2 的否决权未被触发。**

Q5 的检索分数（top-1 **0.3419**）显著低于其余四题（0.55–0.70）。**分数本身可作为拒答的辅助判据**，这对 P3 的实现有直接价值。

### 8.4 切块策略定稿（填补 §8.1 的空白）

| 项 | 实测值 |
|---|---|
| 分段模式 | 父子分段 `hierarchical_model` |
| 父块 | `separator="\n## "`，`max_tokens=2000`，`parent_mode=paragraph` |
| 子块 | `separator="\n"`，`max_tokens=300`，`chunk_overlap=50` |
| 实际段落数 | **16 段**，索引耗时 2–6 秒 |
| 检索模式 | hybrid，向量 0.7 / 关键词 0.3，top_k=5，未启用 rerank |

`retriever_resources` 返回的是**父块**，故引用粒度为整个小节——这对人工核验反而更友好（核验者能看到完整上下文），但需在引用准确率的口径中说明。

### 8.5 发现的问题（P3 必须处理）

**① YAML frontmatter 被当作正文索引，切出 12 个子块 —— 全库最多**

段落 [1] 是 225 字的 frontmatter（`doc_id` / `bu_code` / `effective_from` 等），被切成 12 个子块进了向量库。这是纯噪声，会稀释检索。

处置：切块前剥离 frontmatter，**并把其中字段转为 Dify 的文档元数据**（正是 §8.2 验证的那套接口）。两件事一次做完。

**② 过短的标题块占用 top-k 名额**

段落 [3] 仅 13 字（「1. 适用范围与术语」）。Q3 的 top-2 就是这类块——零信息量却占了一个位置。

处置：设置最小块长度阈值，或将纯标题块并入其后的内容块。

**③ 本轮未验证 rerank**

用的是 `weighted_score` 模式。Q1 的 top-1（0.7049）与 top-2（0.6173）仅差 0.088，加 rerank 有望拉开。留待 P3 结合召回实测再定。

**④ 生成侧 `max_tokens` 需给足**

Q2 的答案在建陶部分被 600 token 截断。不影响本次判定（三个 BU 均已区分），但生产配置须给足。

### 8.6 未纳入本轮的

- **混编 vs 拆分的对比基线**：本轮刻意保留三 BU 混编。结果表明**即使混编，检索与生成也能正确区分三个事业部**——这意味着机制⑤（按 BU 拆文件）的收益低于预期，其价值主要在**权限隔离**（服务端强制注入 `bu_code` 过滤）而非防串答。这一点改变了 §7 中机制⑤ 的定位。
- **引用准确率的量化**：本轮是可行性验证，n=5 不足以给出百分比。正式测量在 P5，用独立的 50 条 RAG 评测集。
