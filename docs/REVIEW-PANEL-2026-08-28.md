## 三、P0 阻塞项（P3 动工前必须定案）

### A. 状态机层

**A1. `interrupt()` 的重放语义与 §12.1 的流程排列正面冲突**

§12.1 把「库存校验 → 生成 `confirm_token` → 生成确认卡片」三个有副作用的动作**全放在 `interrupt()` 之前的同一个节点内**。LangGraph 的中断是靠**重跑 interrupt 所在的整个节点**实现的，官方文档原文：*"Because interrupts work by re-running the nodes they were called from, side effects called before interrupt should (ideally) be idempotent."*

后果：恢复时 `confirm_token` **被重新生成**，用户手上卡片的 token 与之对不上，「一次性校验」直接失效；审计埋点在同一节点内则产生**重复审计行**，而 §12.2 声明仅追加不更新，重复行无法收敛；Supervisor 侧调子图的节点也从头重跑，**若走到 L3 会重新做一次意图识别，可能判出另一个意图**。

处置：把「生成并持久化 token」与「审计埋点」各拆成 `interrupt()` **之前的独立节点**（节点边界即 checkpoint 边界，已完成节点不重放），interrupt 所在节点做到零副作用。库存校验被重放反而是好事——应显式写成「恢复即复检，库存已变则不提交、退回追问」。**约 0.5 人天，事后改需重写下单子图。**

**A2. `write_intent` 表：`confirm_token` 需要独立落点**

三位专家从不同角度指向同一结论。合并处置——新建表：

```
write_intent(
  confirm_token PK, session_id, trace_id, payload JSONB,
  state(pending|confirmed|cancelled|expired), expires_at, result_ref)
```

- 原子一次性消费：`UPDATE ... WHERE state='pending' AND expires_at > now()` 判 rowcount，不用「先查后写」
- 令牌由服务端 `secrets.token_urlsafe(32)` 铸造，**绝不进入送往模型的上下文**，经独立通道交付前端
- 恢复执行时**只读取存储的 payload**，不让模型重新产出参数（同时关掉 TOCTOU 与自我确认两个洞）
- `audit_log` 保持纯追加，确认/取消各插一行，`confirmed_at` 列去掉
- LangGraph 的 interrupt **无内建超时**（官方："waits indefinitely"），TTL 必须自己做

**约 0.5 人天。**

**A3. L2 小模型分类器：两条备选路径各自被自家约束堵死**

§9.2 给 L2 留了两条路，都走不通：Qwen3-8B 路线撞上 §5.2 的「Ollama 与 Dify 错峰」硬约束（一次 S1 请求同时需要两者在线）；embedding + 分类头路线需要标注数据，而全项目唯一的标注数据是 §14 的验收评测集，**拿它训分类器等于训练集测试集同源**，两个指标同时失效。

处置：改用**零训练的 embedding 最近邻**。每意图手写 8–15 条原型话术 → 用已部署的 bge-m3 编码成 centroid → 线上算 cosine，**top1/top2 的 margin 即置信度**，天然提供 L2→L3 的连续判据。零标注、零训练、不新增进程、不触发错峰。**约 0.5 人天，比现方案更便宜。**

**A4. S3 的槽位数与「3 轮上限 + 逐个追问」算术上不相容**

按 `sales_order_line` 的 NOT NULL 字段，S3 至少 9 个必填槽位。首轮填 2–4 个已属乐观，剩余 5–7 个在 3 轮内填不完。而超限兜底「给出已知条件下的最佳结果」**对写操作不适用**——数量未知的订单不能创建。**状态机没有出口**，且 §14 边界用例明列了「追问轮次超限」。

处置：追问策略按意图分档。只读场景保留逐个追问；S3 改为**成组追问**（一次抛出全部剩余必填项，前端 §10.3 规划的 Form 正是这个形态）。上限提到 5 轮或改判据为「连续 2 轮无新增槽位则退出」。**代价为 0。**

**A5. Gateway 分流需要「第四层路由」，但没有设计**

§7.6 让 Gateway 把无状态纯知识问答直通 Dify、其余进 LangGraph。但**判断请求属于哪一类本身就是意图识别**，而三级路由住在 Supervisor 里，在 Gateway **之后**——循环依赖。且 S1（政策 RAG 走 LangGraph）与 D5（色差标准查询直通 Dify）语料同源、关键词空间重叠，Gateway 无从分辨。

处置：PoC 阶段退化为保守规则——仅当「无活跃 LangGraph 会话」**且**「L1 正则命中纯知识白名单」才直通 Dify，其余一律进 LangGraph。**复用同一份 L1 规则表，不引入第四套判据。**

### B. 数据层

**B1. 三张业务表缺三样结构**

| 缺 | 后果 |
|---|---|
| **产品/色号主数据表** | 三张表只有 `product_code` / `color_code`，**没有产品名与色号名**。用户说「白色岩板的库存」，工具入参需要 code——这个映射在数据模型里不存在，S2–S5 四个场景全部受影响 |
| **`production_line` 产线表** | 没有产能，`changeover_min` 就完全不参与运算，§3.2 声称的「延误判定具备真实计算逻辑」是空的——实际只是两个日期比大小 |
| **排产关联到订单行** | `related_order` 指向订单头。一张织染订单常有 3 个色号 = 3 个染缸计划，**无法判断哪条计划服务哪一行**；`process_stage` 还是自由文本无顺序号 |

**合计约 1.1 人天，P2 建表时做成本≈0，P5 才发现是数据重造 + 用例重写 + 三档重跑。**

**B2. 幂等键没有落库位置，也没有唯一约束**

§12.2 承诺「同一 token 只能成功执行一次」，但 `sales_order` 没有任何列存放它。处置：加 `confirm_token VARCHAR(64) UNIQUE`，写入用 `INSERT ... ON CONFLICT DO NOTHING RETURNING`。**整个幂等实现约 10 行。** 另 `order_no` 生成方式未定义，用 sequence 即可。

**B3. 审计表缺「变更前后值」与追溯目标**

宪法第一条明文要求「变更前后值」，`audit_log` 没有。`request_payload` 记的是**工具调用出入参**，不是**业务记录的状态迁移**——订单状态从「已确认」改为「生产中」时，旧值无处留存。加 `target_table` / `target_id` / `before_value JSONB` / `after_value JSONB`，并定死**两段式写入**（独立连接先写 attempt 行 → 业务事务提交/回滚 → 追加 outcome 行，同 `trace_id` 串联），这同时解决「仅追加」与 `confirmed_at` 的矛盾。再加 `REVOKE UPDATE, DELETE ON audit_log` + 触发器，**这是 PoC 阶段防篡改的 90%**。

### C. 安全层

**C1. 全文对 Prompt Injection 零覆盖**

系统把「不可信自然语言 + 不可信检索文本」与「创建订单的写能力」放进同一个 LLM 上下文。最严重的是**间接注入**：§7.4 D1 明确把知识库设计为「业务人员自助传文档」——**任何业务人员都可以往会进入 LLM 上下文的语料里写任意文本**。而「二次确认」防的是模型犯错，不是模型被操纵。

处置（收益最大的一项零成本）：**在 §9.1 拓扑上声明一条不变量——下单子图不摄入任何检索文本，其写载荷只能来自对话槽位与用户确认过的卡片。** 现有拓扑已几乎做到，把它写成约束即可基本关闭间接注入面。配套：检索内容加定界符、通知 webhook 目标固定在配置中不取自模型输出、引用原文纯文本渲染禁用 `dangerouslySetInnerHTML`。**测试集加 6–8 条注入用例——这应视为 PoC 的产出而非成本**，「让 LLM 持有写权限的注入风险有多大」正是规模化决策最需要的数据点。

**C2. 宪法缺第十条「不可信输入」**

九条原则覆盖了写路径、向量写入权、async、Gateway、模型抽象、机密、脱敏、引用溯源，**唯独没有一条约束「不可信文本能做什么」**——这是 C1 与权限缺失的共同根因。

### D. 环境层

**D1. 16GB 内存核算不成立**

Dify 1.17 实起 **13 个必起容器**（含文档从未提及的 `local_sandbox`、`agent_backend`、`agent_ssrf_proxy`、`worker_beat`），且 **`sandbox` 与 `local_sandbox` 没有 `profiles` 键，「不启 sandbox」在 1.17 上做不到**；`.env.example` 实测 `CELERY_WORKER_AMOUNT=4` 而非文档假设的单 worker。加上被漏计的 Embedding/Rerank（2.5–4.5 GB）、Docker Desktop VM（1.0–1.5 GB）、macOS 基线（实测已占约 9.6 GB），**重估中位约 18.7 GB**。

后果不只是卡：统一内存进 swap 后本地检索与 rerank 耗时漂移，而 **§14 的 P50 延迟与 10 并发压测结论都在这台机器上测**——核心交付物的数据会被污染。

处置：**Embedding / Rerank 改走百炼 API**（省 2.5–4.5 GB + 消除 CPU 重排延迟 + 省整个部署工作，成本≈0，数据边界与 §6.1 已有声明一致）；`.env` 显式设 `CELERY_WORKER_AMOUNT=1` 并去掉 `collaboration` profile；Docker Desktop 限内存 6–7 GB；**§5.2 的退路数字「2 核 4G 云主机」应改为 2 核 8G**。

**D2. R15 的处置方式在 Dify 1.17 上不正确**

文档写「从 `COMPOSE_PROFILES` 中移除 `postgresql` 与 `pgvector`」。但 1.17 的 `.env.example` 实测是**插值派生**的：

```
COMPOSE_PROFILES=${VECTOR_STORE:-weaviate},${DB_TYPE:-postgresql},collaboration
```

设 `VECTOR_STORE=pgvector` 后它会**自动重新包含 `pgvector`**，容器照起——R15 想避免的第三个 PG 实例原样出现。正确做法是**显式覆写为字面量**。另 `PGVECTOR_HOST` 不在 1.17 的 `.env.example` 里，R15 给的变量名**未经核实**。

**D3. 全文档没有任何备份方案**

「备份」二字只出现在「选 pgvector 可以少一套备份策略」这个**理由**里。唯一权威 PostgreSQL 与 Dify 知识库都在一台笔记本上，宪法第一条要求审计不可篡改——**没有副本的单机数据库不满足这一条的实质**。比磁盘故障现实得多的杀手是 `docker compose down -v`，而 R15 的处置正要求反复调整 compose。

好消息：按 R15 把 Dify 元数据 + 向量都收进外部 PG 后，**两条 `pg_dump -Fc` 同时覆盖业务数据、审计、checkpoint、知识库、segment、标注和向量**——这是 pgvector 选型一个未被论证到的实打实好处。**0.25 人天做，0.1 人天演练。没恢复过的备份不算备份。**

### E. 方法论层

**E1. 「≥90% 端到端成功率」没有定义「成功」**

全篇没有判定谓词。查询类场景中「成功」是调对了 API、返回了对的数据、还是措辞也对？多轮澄清里第一问问偏但最终收敛算不算？**没有事先冻结的评分细则，≥90% 不可证伪**，而由同一人在看到结果后拟定细则，标准会无意识地向观测结果对齐。

处置：把「评分细则 + 标准答案 + 标准引用」作为 **P2/P3 交付物**，实现完成前 commit 进 git，报告中注明冻结 commit 号（**预注册**）。**0.5 人天，是对报告可信度提升最大的一笔投入。**

**E2. 样本量 + 单次运行 + 自出题自判卷，三重叠加**

每场景 6 条，分辨率 16.7 个百分点——**「≥90%」在单场景层面根本无法表达**。整体 36/40 的 95% 置信区间约 76%–97%，「达标 90%」与「实际 80%」在此样本量下不可区分。用于 M2 vs M3 *比较* 时，n=40 大约只能检出 15–20 个百分点以上的差距。且全文未见温度/随机种子设定，**运行间方差与档位间差异完全混淆**，1 条 flake 就是 2.5 个百分点。

处置：固定 temperature 与 seed 并写进报告；核心两档各跑 3 次取多数（机器时间为主）；**请业务方用自己的话出 10–15 条题**（开发者成本≈0，是效度问题最强的解药）；引入 LLM-as-judge 作第二判卷人并给出人机一致率；每个数字标注 n 与置信区间。

**E3. 成本维度没有 TCO 模型——而它是唯一真正驱动决策的维度**

brief 四维现状：数据安全性已声明无实测证据；准确率证据弱（E2）；延迟可测但被混淆；**成本是唯一真正决定「自建还是用 API」的维度，而计划产出的将是误导性数字**——AutoDL 按小时租用、只在评测时开机几小时的费用不是自部署成本，自部署 TCO 含硬件摊销、电力、运维人力，以及最关键的**闲置成本**。

**四个对比维度：一个作废、一个证据弱、一个被混淆、一个缺模型——这套对比目前支撑不了它存在的目的。**

处置：新增参数化 TCO 模型（假定日均请求量与 token 量，输出自建/托管的月成本交叉点），0.5–1 人天，**这是整份报告里对决策最有用的一页**。同时把「数据安全性」改为可实证的替代命题——**演示「同一测试集，仅改配置即完成 M2↔M3 切换，业务代码零改动」**，这是宪法第六条本就要求的，关于**可迁移性**的硬证据。

**E4. 工期：36 人天从未做过自下而上分解**

工作量轨迹 30 → 31 → 31.5 → 36，每次变动都是「补记漏项」。**一个只会因遗漏而单向上调的估算，说明基数是自上而下拍的。** 而任务级 WBS 被列为 P5 交付物——本该用来做估算的工具排在项目结束时产出。

| 阶段 | 文档 | 独立重估 | 主要差异来源 |
|---|---|---|---|
| P1 | 4.0 | **6.5** | **AutoDL + vLLM 首次部署（65GB 权重 + 显存调参）全文未计工** 1.5；Dify 指向外部 PG18 实为 1.5 而非 0.5 |
| P2 | 5.5 | **6.5** | 跨表自洽的模拟数据实为 2.0 |
| P3 | 10.5 | **16.0** | React 六组件 4.5（文档隐含约 2）· 8 份业务文档 2.5 · 五子图 3.0 |
| P4 | 9.0 | **10.0** | 最接近准确的一段 |
| P5 | 7.0 | **12.0** | **八份交付文档 4.5** · 评测框架 1.5 · 120 次运行 1.0 · 逐条人工核验 1.0 |
| **合计** | **36.0** | **51.0** | |

另有方法论问题：**「36 人天 ÷ 5 天/周 = 7.2 周」把人天当成了日历工作日**，隐含 100% 投入。按单人项目现实的每周 4 有效人天，36 人天本身就对应 9 周。

加上本次评审的净增项，总量约 **54.5 人天**。

## 五、需要用户决策的三件事

### 决策一：AI 辅助程度

交付管理专家把这列为其重估的**头号不确定源**：

> 若绝大部分实现代码与 16 份文档的初稿由 AI 生成、人只做审阅与整合，文档撰写工作量可降 40–50%……这个假设一变，51 人天可能落在 **40–60** 的区间里。

他按「中度辅助」估的。**本项目的实际工作方式直接决定这个数字往哪边走。**

### 决策二：8 周是否硬约束

若是，专家给出了具体方案——**砍到三场景**：S1（政策 RAG）、S2（库存多轮澄清）、S3（创建订单写路径），约 30–32 人天。

论证：这三个已完整覆盖 §1 列出的**全部四项待验证能力**（自然语言读+写、静态知识与动态数据融合、LLM 与业务 API 双向打通、RAG/Workflow/RPA 集成），**砍的是广度不是深度，brief 的 5 项交付物一项不少**。

若不是硬约束，则按 54.5 人天 ÷ 每周 4 有效人天 ≈ **13.6 周**，含 30% 缓冲约 16 周。

### 决策三：砍范围优先级（按「决策价值/成本」排序，可砍出约 7.5 人天）

1. 《向量数据纳管服务设计》11 节 → **1 页附录**（省 1–1.5，决策影响为零；§2.3 自己写明本期不会有人实现它）
2. P5 的 **pgvector→Qdrant 切换验证与全量重跑**（省 1.0）——验证的是内部设计主张而非业务问题
3. **通知渠道 4 → 1**（省 1.0，同时消掉三个 IM 平台的外部凭据依赖）
4. **Dify 12 项 → 6 项**（省 1.5–2.0）：保留 D1/D2/D5/D7/D12/D3
5. **M1（4090）档**（省 1.0–1.5）——核心对照组是 M2 vs M3，M1 的成本数据点可由 M2 吞吐 + 4090 报价推算
6. **模拟遗留 ERP 降为单页表单**（省 1.5）——保留降级判定链路与审计留痕，砍的只是被自动化对象的体量
7. **10 并发压测 → 3 并发冒烟 + 书面外推**（省 0.5）

**不可砍**：8 份知识文档与模拟数据的真实感 · 写路径的二次确认+审计+幂等 · React 对话界面 · 评测严谨性 · 从零落地手册。

> ⚠️ **砍完这 7.5 人天仍是约 47 人天，闭合不了 8 周的缺口。范围与工期必须一起动。**

## 六、专家一致肯定的

- **§6.1 的结论边界声明**——主动宣布「数据安全性一维在 AutoDL 上无法取得实测证据」，宁可作废一个维度也不糊弄。六位中有五位单独点名了这一条
- **写路径唯一 + Dify 不落库**这条红线画在了正确位置，且从 §7.2 → 宪法第二条 → §7.5 是贯通的
- **排除双写向量库的论证**——追到「引用溯源断裂 → 直接击穿 ≥85% 引用准确率指标」这个具体验收指标上，而非停在「数据一致性」
- **排除 GraphRAG 的理由**——community summary 的溯源粒度与引用准确率指标直接冲突，是技术性理由而非「太复杂」
- **v1.3 的自我推翻**——明确写下 v1.2 的论证缺陷（推翻一条论据后未重审其余即改选）
- **版本矩阵直查 registry 而非凭记忆**，并写明证据边界（「本次仅核实 release notes 文本，未实测连接」）
- **R15（Dify 默认 compose 会额外起 PG 容器）在写代码前就被发现**——只有真读了 compose 文件才会发现
- **M2 vs M3 作为核心对照组**的实验设计是干净的
- **单 PostgreSQL 实例承载四类负载**在本项目规模下完全合理；**没有为 100–1000 行的表设计索引和分区**也是对的
- **`delta_e` / `changeover_min` / `same_batch_req` 三个字段的存在本身**说明设计者懂这两个行业
