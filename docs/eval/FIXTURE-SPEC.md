## 1. 为什么均匀随机生成不行

P0-2 造数据时 `bu` 与 `year` 都用 `i % 2`，两维完全相关，四维过滤查询**直接
返回 0 行**。这不是理论风险，是本项目已经发生过的事故。

均匀随机同样产不出关键形态：跨缸澄清需要「同一 (product, color) 有 ≥3 个批次
且缸间 ΔE 差值 >1.0」，随机撒点几乎不会命中。**关键形态必须被显式构造**，
再由断言校验兜底。

## 2. 规模约束：少品种、多批次

算一遍：100 条库存批次，若要每个 `(product, color)` 平均有 3 个批次（跨缸
澄清的前提），只能支撑约 33 个组合，再乘等级维度 →

| 维度 | 规模 | 理由 |
|---|---|---|
| 每 BU 的 SKU | **10–15** | 按 SKU 铺开会让绝大多数组合只有 1 个批次 |
| 每 BU 的色号 | **6–8** | 同上 |
| 库存批次 | ≥100 | 验收要求每表 ≥100 |
| 产线 | 每 BU 4–6 条 | 够排出队列，能演「插单排到队尾」 |
| 订单 | ≥100（头），行数 ≥150 | 一单多行才有「三个色号三条计划」的粒度 |

**「少品种、多批次」是硬约束。** 违反它，招牌的跨缸澄清演示直接没数据可演。

### 2.1 ⚠️ 与「每表 ≥100 条」的冲突

设计文档 §4.1 写「三类业务数据，**每表 ≥100 条**」。这条与「少品种多批次」
**直接矛盾**：每 BU 10–15 个 SKU，三个 BU 合计只有 30–45 个产品。

**裁决：≥100 只适用于交易类表，主数据不适用。**

| 表 | 规模 | 依据 |
|---|---|---|
| `sales_order` / `sales_order_line` / `inventory_batch` / `production_plan` | ≥100 | 原文的 ≥100 |
| `product` / `color` / `production_line` | 40 / 21 / 15 | 少品种多批次硬约束 |

理由：≥100 的意图是「数据量足以让查询有区分度」，而主数据的区分度来自
**组合**而非条数 —— 40 个产品 × 21 个色号已能产生 800+ 组合，远超 110 条批次
能覆盖的范围。硬把主数据铺到 100 条，反而让每个组合平均不到 1 个批次，
把跨缸澄清的数据基础直接抽掉。

这不是放宽标准，是两条要求冲突时选了保住场景的那条。**若评审认为应以 ≥100
为准，需同时放弃跨缸澄清场景** —— 两者不可兼得。

## 3. 用例 → 数据条件 → 断言

### 3.1 主线场景

| 用例 | 依赖的数据形态 | 断言（P2.2.3 实现） |
|---|---|---|
| **S1** 查营销政策 | 不依赖业务表（走 RAG）；但需 `policy_code` 在订单上有取值，供 S1↔S4 交叉提问 | `sales_order.policy_code` 非空的行 ≥20 |
| **S2-01** 普通查库存 | 任一 `(bu, product, color)` 有可用量 >0 | 存在 |
| **S2-03** 跨缸澄清 | 存在 `(product, color)` 拥有 **≥3 个批次**，且批次间 ΔE 差值 **>1.0** | `HAVING count(*)>=3 AND max(delta_e)-min(delta_e)>1.0` ≥3 组 |
| **S2-05** 同缸约束 | 存在订单行 `batch_policy='SAME_BATCH'` 且单批可用量 < 需求量 | 存在 |
| **S3-01** 正常下单 | 存在有效 `(product, color, 等级)` 且库存充足 | 存在 |
| **S3-05** 库存不足 | 存在订单行需求量 > 该 `(product,color)` 全部可用量之和 | 存在 ≥3 行 |
| **S4-01** 查订单进展 | 各状态均有订单：待评审/已确认/生产中/部分发货/已完成 | 五种状态**各** ≥5 单 |
| **S4-04** 部分完成 | 存在计划 `0 < qty_completed < planned_qty` | 存在 ≥10 条 |
| **S5-01** 查排产 | 存在订单其订单行关联 ≥2 条计划（多工序） | 存在 ≥20 单 |
| **S5-02** 真延误 | 存在订单其**末道工序** `plan_end > required_date` | 存在 ≥8 单 |
| **S5-04** 不延误 | 存在订单末道工序 `plan_end <= required_date`（阴性对照） | 存在 ≥8 单 |
| **S5-06** 联动分析 | 存在订单行关联 ≥3 条计划且 `stage_seq` 连续，可推「延一道影响后两道」 | 存在 ≥5 组 |

> **S5-04 单列的理由**：只有延误样本时，一个恒答「会延误」的模型也能拿满分。
> 阴性对照是判据可证伪的前提 —— 与评分细则 §1.2 同一原则。

### 3.2 边界

| 用例 | 依赖的数据形态 | 断言 |
|---|---|---|
| **边界-02** 跨 BU 歧义 | 存在两个不同 BU 的产品 `product_name` 高度相似 | 存在 ≥2 对 |
| **边界-04** 同名色号异义 | 同一 `color_code` 在 ≥2 个 BU 下存在且 `color_name` 不同 | 存在 ≥3 个 |
| **边界-07** 待检批次 | 存在 `qc_status='待检'` 的批次 | ≥10 条 |
| **边界-08** 让步接收 | 存在 `qc_status='让步接收'` 的批次 | ≥5 条 |
| **边界-09** 越权查询 | 每个用户的 `bu_codes`/`regions` 之外**都有**数据存在 | 对 users.yaml 每个用户，域外行数 >0 |
| **边界-10** 深色系例外 | 存在 `color.is_dark=true` 的色号且有对应批次 | ≥3 个色号 |

> **边界-09 的断言方向容易写反**：要断言的是「域外**有**数据」，不是「域外没有」。
> 若域外本来就没数据，越权测试通过与否毫无意义 —— 模型什么都不做也能"通过"。

### 3.3 参照完整性（不建外键的补偿，§4.0）

| 检查 | 断言 |
|---|---|
| 订单行的 `order_no` 都能对上 | 孤儿行数 **= 0** |
| 计划的 `related_order_line` 都能对上（非空的那些） | 孤儿行数 **= 0** |
| 三张业务表的 `product_code` 都能对上 | 孤儿行数 **= 0** |
| `(bu_code, color_code)` 都能对上 | 孤儿行数 **= 0** |
| 计划的 `line_code` 都能对上 | 孤儿行数 **= 0** |
| **`bu_code` 与主数据一致** | 业务表的 `bu_code` ≠ `product.bu_code` 的行数 **= 0** |

> 最后一条是 §4.1.1 点名的形态：一行完全可能是 `bu_code='BU-A'` 配一个瓷砖的
> `product_code`。**只查「code 存在」查不出它** —— code 是存在的，只是属于别的 BU。

### 3.4 单位一致性

| 检查 | 断言 |
|---|---|
| 订单行 `uom` = 对应 `product.default_uom` | 不一致行数 = 0 |
| 库存 `uom` = 对应 `product.default_uom` | 不一致行数 = 0 |
| 计划 `uom` 与产线 `capacity_uom` 可比 | 不一致行数 = 0 |

> ETA 公式 `planned_qty / capacity_per_hour` 隐含「单位一致」。数据库不校验它，
> 这里必须查 —— 否则算出的工时会静默差几个数量级。

## 4. 固定随机种子

生成器用固定种子（`SEED = 20260910`）。理由不是「可复现」这么笼统 ——
是**评测结果必须可归因**：某条用例失败时要能区分「模型不行」与「这次的数据
恰好刁钻」。种子一变，两者无从分辨。

种子写死在代码里而非配置：能改的东西迟早会被改，而改了之后所有历史评测结论
的可比性一起失效。
