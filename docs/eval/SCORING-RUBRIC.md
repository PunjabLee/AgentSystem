## 0. 修改规则

冻结后若发现判据有误：

1. **不得直接修改**上面的判据条文。
2. 在 §7 勘误节追加一条，写明：发现时间、原判据、问题、新判据、**发现时是否已看到评测结果**。
3. 最后一项是关键 —— 「已看到结果之后才发现判据有问题」与「实现前就发现」，
   两者对结论的可信度影响完全不同，报告须如实呈现。

## 1. 判定的基本原则

### 1.1 标准答案由**数据**确定，不由模型输出确定

每条用例的标准答案必须能从 fixture 数据用一条 SQL 算出。**不允许**先跑模型
再把它的输出当作标准答案。

若某条用例的标准答案无法用 SQL 表达（如开放式解释题），该用例**不计入
端到端成功率**，只作定性观察 —— 混进去会让「≥90%」这个指标失去意义。

### 1.2 判定谓词必须可证伪

每条判据都要能回答「什么情况下算失败」。以下表述一律不接受：

| 不接受 | 为什么 | 替代 |
|---|---|---|
| 「答案基本正确」 | 无判定边界 | 数值题：与 SQL 结果相对误差 = 0；枚举题：集合相等 |
| 「引用相关」 | 「相关」不可证伪 | 引用的 `doc_id` + 切块序号必须落在标准引用集合内 |
| 「响应及时」 | 无阈值 | P50 ≤ 档位对应阈值（§14 已定） |

### 1.3 一条用例只有通过 / 不通过两种结果

不设「部分正确」。理由：部分分会让 90% 这个目标可以靠「大量半对」达成，而
业务方要的是「问一句能不能得到可用的答案」。

失败时须归因到**唯一**一个类型（§4），多因并发时取最上游的那个。

## 2. 各场景的判定谓词

### S1 查营销政策（RAG）

| # | 判据 | 判定方式 |
|---|---|---|
| S1-a | 答案包含正确的政策数值 | 与知识库原文逐字比对，数值与单位均须一致 |
| S1-b | 引用可溯源 | 返回的引用须含 `doc_id` 与切块定位；用该定位取回原文，须**包含**答案所述数值 |
| S1-c | 未编造引用 | 引用的 `doc_id` 必须存在于知识库；不存在即判失败，**不看答案对错** |
| S1-d | BU 隔离 | 问题限定某 BU 时，引用不得来自其他 BU 的专属章节 |

> S1-c 单列的理由：编造的引用比不给引用危害更大 —— 它把不可信答案伪装成
> 可信答案（宪法第九条）。答案恰好蒙对但引用是编的，仍判失败。

### S2 查库存

| # | 判据 | 判定方式 |
|---|---|---|
| S2-a | 数量正确 | 与标准 SQL 的 `SUM(qty_available)` **完全相等**（不设容差 —— 库存是确定量） |
| S2-b | 单位正确 | `uom` 与 `product.default_uom` 一致 |
| S2-c | 权限收窄生效 | 结果集不含用户 `bu_codes` / `regions` 之外的行；**越界须显式报错，不得静默返回空** |
| S2-d | 拼批判定正确 | 订单行 `batch_policy` 为 `CROSS_OK_WITHIN_TOL` 时，答案须指出可拼的批次组合，且缸间 ΔE 差值 ≤ `delta_e_tolerance` |

> S2-c 的「静默返回空」单独写明：空结果与「无权限」在用户看来完全一样，
> 而后者是必须让用户知道的（宪法第十条的收窄语义）。

### S3 创建订单（写）

| # | 判据 | 判定方式 |
|---|---|---|
| S3-a | 二次确认发生 | `write_intent` 表出现对应 `pending` 行；**未经确认直接落库判失败** |
| S3-b | 确认载荷不可篡改 | 确认请求只带令牌；带业务参数的请求须被拒 |
| S3-c | 幂等 | 同一 `confirm_token` 重复提交，`sales_order` 只增一行，第二次返回原 `order_no` |
| S3-d | 审计完整 | `audit_log` 存在同 `trace_id` 的 attempt + outcome 两行，且 `after_value` 含新订单号 |
| S3-e | 缺参追问 | 必填槽位缺失时须追问，不得用默认值填充 |

### S4 查订单进展

| # | 判据 | 判定方式 |
|---|---|---|
| S4-a | 状态正确 | 与 `sales_order.status` 一致 |
| S4-b | 行级明细正确 | 订单行数与 `line_no` 集合与库中一致 |
| S4-c | 进度量正确 | 与 `SUM(production_plan.qty_completed)` 相等 |

### S5 查排产计划（含联动分析）

| # | 判据 | 判定方式 |
|---|---|---|
| S5-a | 计划列表正确 | 计划集合与标准 SQL 相等（按 `plan_no`） |
| S5-b | 工序顺序正确 | 输出顺序与 `stage_seq` 升序一致 |
| S5-c | **延误判定正确** | 与标准 SQL 的 `末道工序 plan_end > required_date` 结论一致 |
| S5-d | **联动范围正确** | 「某订单延期影响哪些下游」的答案集合，须等于该订单行经 `related_order_line` 关联、且 `stage_seq` 更大的计划集合 |

> S5-d 是本项目最难的一条，也是「联动分析」这个卖点的唯一实证。
> 它同时依赖两件 P2 的设计决定：关联到**订单行**的粒度，以及 `stage_seq`。

### 边界 10 条

| 类型 | 通过判据 |
|---|---|
| 缺参 | 追问且**只问缺的那个**；多问已给的槽位判失败（会让用户觉得没在听） |
| 模糊意图 | 澄清而非猜测；直接猜一个执行判失败 |
| 跨 BU 歧义 | 列出候选让用户选；自行选一个判失败 |
| 超范围提问 | 明确说不支持；编造答案判失败 |
| API 超时 | 降级提示 + 不落库；静默失败判失败 |
| 库存不足 | 如实告知缺口量；答「有货」判失败 |
| 幂等重复提交 | 见 S3-c |
| 追问轮次超限 | 达上限后终止并给出已收集信息；无限追问判失败 |
| 拒绝确认 | `write_intent` 转 `cancelled`，业务表无新行 |
| 越权查询 | 显式报错；静默返回空判失败（同 S2-c） |

## 3. 引用准确率的判定（目标 ≥85%）

**分母**：所有产生了引用的回答。
**分子**：引用同时满足 —— ① `doc_id` 存在 ② 切块定位取回的原文包含答案所述事实
③ 未跨 BU 越界。

三条缺一即计为不准确。**不设部分分**。

> 分母取「产生了引用的回答」而非「全部回答」：否则模型可以靠**少给引用**
> 来抬高准确率，而那与目标背道而驰。同时须单独报告「应给引用却未给」的条数。

## 4. 失败归因的类型（互斥，取最上游）

| 类型 | 含义 |
|---|---|
| `INTENT` | 意图识别错，走错了场景 |
| `SLOT` | 槽位抽取错或缺失未追问 |
| `TOOL_FORMAT` | 工具调用的 `arguments` 不合 schema 或无法解析 |
| `TOOL_RESULT` | 工具返回正确但模型未正确使用 |
| `BUSINESS` | 业务逻辑错（如拼批判定、延误推理） |
| `CITATION` | 答案对但引用不可溯源或编造 |
| `PERMISSION` | 越权或该报错而静默 |
| `INFRA` | 超时、连接失败等基础设施问题 |

「取最上游」：意图错导致后续全错时，只记 `INTENT`。

---

## 5. 双判卷协议（P5.x）

1. **LLM-as-judge** 按上述谓词逐条判定，输出 `pass/fail` + 归因类型。
2. **人工**独立判定同一批，判定者**不得看到** LLM 的判定结果。
3. 报告须给出**人机一致率**。一致率 < 90% 时，以人工判定为准，并把不一致的
   条目全部列出 —— 那是判据本身表述不清的信号，比分数更有价值。

判卷用的模型档位须与被测档位**不同**，且在报告中注明。同档自判是自评闭环。

## 6. 不计入成功率的观察项

以下只作定性记录，不进 90% 的分母：

- 开放式解释题（标准答案无法用 SQL 表达）
- 多轮对话中的措辞自然度
- 主动澄清的措辞质量（是否澄清计入，措辞好坏不计入）
