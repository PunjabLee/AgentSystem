**P1 的地基是稳的，但宣布它通过的那套机制不稳。**

两位独立评审都没有提出架构级返工项 —— 两段式审计、三层防篡改、`ALTER DEFAULT
PRIVILEGES` 前置，这些机制经过了对抗性验证，不是纸面设计。问题集中在两层：

团队只有 1 人时，**打破自评闭环性价比最高的手段**：它提供一个团队控制范围之外、无法预先调好的执行环境。

## 三、关口结论的前提：两条判定漏洞（**建议合入 main 前修**）

这两条按严重度定义属「重要」（补救在脚本层，代价 0.2 人天），但它们是**本次评审要回答的问题本身** ——
判据不可靠，「P1 通过」这个结论就没有支点。

### 3.1 判据 1：档位可静默缩水，仍报 PASS

`scripts/chat.py:90` 取 `tiers = config.available_tiers`（只含 `available` 的档），末行
`return 0 if all(results.values()) else 1`。`all()` 对**缩水后的集合乃至空集合**都返回 True，
而 `scripts/p1_exit.sh:20` 只读退出码。

**实测**：抹掉 `AUTODL_ART_API_KEY` 模拟 M3 密钥过期 → `chat.py` **退出码 0**，判据 1 报 PASS，
实际只跑了 M0 与 M4 两档。

> 汇总人自我更正：此前我向决策者报告「判据 1 的退出码逻辑经得起查，任一档失败都会非零退出」。
> 该结论只对**跑了的档位**成立。我当时只读了 `return` 那一行，未上溯 `tiers` 的来源 ——
> 正是评审失败模式 R1「只看一层就断言」。

**修**：`chat.py` 加 `REQUIRED_TIERS = {"M0","M3","M4"}`，缺档即返回 1。**0.1 人天**。

### 3.2 判据 2：分不清 PASS 与 SKIP

`p1_exit.sh:26-42` 点名跑两个核心用例，注释写明「不能只看 pytest 退出码 —— 必须确认这两个
用例确实存在且通过」，**实现依然只看退出码**。

**实测**：`assert False` 的用例被 `@pytest.mark.skip` 标记后，pytest **退出码 0**。

讽刺的是 `.github/workflows/ci.yml:96-101` 专门写了 grep `skipped` 的二次校验 ——
但那个 CI **从未运行过**。检查写对了地方，却写在唯一不执行的地方。

**修**：给这两次调用加 `-rs` 并 grep `SKIPPED`，与 `ci.yml` 对齐。**0.1 人天**。

## 四、P2 准入的阻塞项

### 4.1 🔴 `interrupt()` 节点在 resume 时从头重放 —— 约束须在写下单端点**之前**固化

**实测**（langgraph 1.2.11 + Python 3.14.6）：含 `interrupt()` 的节点，其 `interrupt` **之前**的
代码在 resume 后执行了 **2 次**；中断前已完成的**其他**节点不重跑。

设计方向本来就对 —— 主设计 L2 把「提交」排在 `interrupt()` 之后，P2 设计给
`sales_order.confirm_token` 加了 UNIQUE 兜底，主设计 §15 也把「`interrupt()` 拓扑拆分」列入 P3。
**缺的不是认识，是不可违反的规则**：P2.3.4 即将写下单端点，此刻把
「写操作绝不与 `interrupt()` 同节点」「`confirm_token` UNIQUE 不得移除」写进宪法并加机械检查，
代价最小；等子图写完再改就是拓扑返工。

**修**：宪法补一条 + 一个 AST 机械检查。**0.3 人天**。

### 4.2 🔴 `langgraph` 本体未安装，且官方未声明支持 Python 3.14

`pyproject.toml` 只声明了 `langgraph-checkpoint-postgres`。PyPI 上 langgraph 1.2.11 的
classifiers 只到 **3.13**（`requires_python: >=3.10` 是开放上界，故装得上但未背书），
本项目跑 **3.14.6**。宪法第二条要求写路径必经 LangGraph。

**实测**：在临时环境里装 1.2.11，import / 构图 / invoke / interrupt / resume **全通**。
风险可控，但应显式记录这是「实测可用而非官方支持」。

**修**：正式加入依赖并把探针固化为一个测试。**0.2 人天**。

## 六、汇总人裁决：驳回与下调

### 6.1 【驳回论据，保留观察】`production_plan.related_order` 缺外键

评审者称：「同一段落里 `product_code`/`color_code`/`line_code` 都显式声明了外键，却唯独漏了
这一个最关键的关联列。」

**实测核对**：`production_plan` 的 DDL 里 **一处 `REFERENCES` 都没有**。九张表逐一统计，
只有 `sales_order_line` 有 1 处外键，其余全部为 0。

**裁决**：
- **保留**观察 —— `related_order` 确无外键，且以订单头为粒度**无法回答**「一张订单三个色号
  对应三条产线计划」，而这正是 S5 联动分析要答的问题。这一点成立且重要。
- **驳回**论据 —— 「唯独漏了它」不成立。整套 DDL 几乎都没有外键，这是一个**面向 PoC 种子数据的
  统一取舍**，不是针对某一列的疏漏。
- **影响**：修复范围从「补一个外键」变成「决定这套 DDL 要不要外键」，是**决策题不是工程题**，
  应进第七节交决策者，而非直接排进 P2.1.5。

### 6.2 【下调】「有 2 条悬挂 attempt 无人发现」

这是**汇总人自己**的初版措辞。收窄到 `action_type='write'` 后：**60 条写操作，0 条悬挂**。
那 2 条是防篡改测试直接用 SQL 播的种子，未走装饰器。

**裁决**：下调为「『可检测』这个**性质**缺少检测手段」（第 5.3 条），而非「存在未被发现的失败」。
两段式机制本身工作正常。

### 6.3 【不采纳】两位评审均称「未发现阻塞项」

两位独立评审都明确表示没有架构级返工项。**汇总人不完全同意**：第 4.1 条（`interrupt()` 重放）
符合阻塞定义 —— 补救手段在上游，且 P2.3.4 一旦写完再改就是子图拓扑返工。

两位没提到它，是因为**没有人被派去查 LangGraph 的执行语义**（我原本派了这个视角，但那一轮
四个评审者全部因额度超限掉线）。这条印证了评审技能里的一句话：**最有价值的发现往往只有
一位评审者指出，因为只有他去查了框架的执行语义文档。**
