# 架构评审要点结构

评审的价值不在于找到多少问题，而在于**找到那些会在实施中途爆炸、且当时已无退路的问题**。一条在动工前 0.5 人天能改掉的拓扑缺陷，写完代码再改就是重写整个子图。

本技能分三部分：**怎么组织评审**、**怎么处理评审结果**、**查什么**。

---

## 一、组织评审：视角切分与防注水

### 视角必须互不重叠

评审的信号来自**独立视角的收敛**。如果三个评审者视角高度重合，他们指出同一个问题不构成任何额外证据——那只是回声。切分时让每个视角有自己的专业判据来源：

| 视角 | 独有判据 |
|---|---|
| 领域实现（RAG / 前端 / 具体技术栈） | 该技术栈的实际能力边界与已知陷阱 |
| 状态与编排 | 框架的执行语义（重放、检查点、中断恢复） |
| 数据与后端 | 数据模型能否支撑业务推理；事务与幂等 |
| 环境与运维 | 资源核算、部署拓扑、可观测性、演示日风险 |
| 安全与合规 | 攻击面、审计完备性、权限模型 |
| 交付管理 | 估算方法、指标可证伪性、决策转化 |

**互不知情是关键**——并行派发，不让他们看到彼此的结论。

### 评审指令里必须有的四条约束

不给约束，评审者会系统性地朝三个方向漂移：凑数、按生产标准苛求、无限加需求。

1. **「不要为凑数编造问题。某部分确实没问题就直接说没问题。」**
2. **「这是 <PoC / MVP / 内部工具>，不是生产系统，不要用生产级标准苛求。」**——并说明哪些是例外（通常是审计、安全红线）
3. **「团队只有 N 人、预算 M。任何『建议增加 XX』必须评估工作量代价并说明拿什么换。」**
4. **「凡涉及具体 API 能力、字段、版本行为，请实际查证源码或官方文档，不要凭记忆断言；查不到就写进『我不确定的地方』，不要重试。」**

第 4 条的后半句有实际原因：反复重试外部查证是评审 agent 掉线的主要原因。**限制查证次数比允许无限查证更可靠。**

### 强制要求的输出结构

```
## 总体判断（一到两句）
## 发现（按 阻塞 > 重要 > 建议 排序）
   每条：位置 / 问题 / 依据（要有技术依据，不要空泛）/ 建议（含代价）
## 做得对的地方（简短，不要客套）
## 我不确定的地方
```

**「我不确定的地方」是整个结构里最有价值的一节。** 它把「查证过的结论」和「基于经验的推断」分开，决定了汇总时哪些能直接采纳、哪些要自己复核。没有这一节，两者混在一起无法区分。

## 二、汇总裁决：不转述，先验证

**汇总者的职责是裁决，不是传话。** 一条引用了具体文件路径和 issue 编号的结论，仍然可能是错的。

### 必须自己验证的三类结论

| 类别 | 为什么 |
|---|---|
| **会导致架构改动或返工的阻塞项** | 错误的阻塞项会让你付出不必要的工期与复杂度 |
| **与已有实测证据冲突的结论** | 评审者的信息可能比你旧 |
| **断言「某能力不存在」的** | 这类最容易错——看了一层没找到就下结论，而能力嵌在下一层 |

第三类有个具体的失败模式值得记住：评审者查了某 API 的顶层参数列表，发现没有想要的字段，就断言「不支持」。实际上该字段嵌在其中一个**参数对象的内部**。**「我在这一层没看到」不等于「它不存在」——多往下看一层。**

### 收敛计数，但不迷信

统计每条问题被多少位独立评审者指出。收敛数高的优先处理——那是多个专业视角同时验证的结果。

**但收敛数不等于重要性。** 今天最有价值的一条发现（框架的节点重放语义与确认流程排列冲突）只有一位评审者指出，因为只有他查了框架的执行语义文档。**收敛用于排序，不用于筛选。**

### 证据时效性优先于评审结论

如果评审期间出现了新的实测证据（用户跑通了某个组合、某个版本发布了），**证据推翻结论，不是结论推翻证据**。明确说明该评审者写作时不掌握这一信息，然后驳回。

## 三、七层要点清单

### 第 1 层：需求与验收（最常被跳过，返工最贵）

- [ ] **每条验收指标有判定谓词吗？** 「成功率 ≥90%」——什么算「成功」？调对了 API、返回了对的数据、还是措辞也对？多轮追问第一次问偏但最终收敛算不算？**没有事先冻结的评分细则，指标不可证伪。**
- [ ] **每条验收指标有可测试的对象吗？** 常见失败：测试集里列了「越权查询」，而设计里根本没有权限模型——该指标没有实现物可测。
- [ ] **样本量能表达指标精度吗？** 每场景 6 条用例 = 16.7 个百分点的分辨率，「≥90%」在单场景层面根本无法表达。n=40 时 90% 的 95% 置信区间约 76%–97%。
- [ ] **谁出题、谁判卷？** 同一人写测试、跑测试、判对错、并写「我的方案是否可行」的结论——全部偏差同向。低成本解药：让需求方用自己的话出题；引入第二判卷人给出一致率。
- [ ] **单次运行还是多次？** 没有固定温度与随机种子的单次运行，运行间方差与被比较的差异完全混淆。
- [ ] **立项目标在架构里都有落点吗？** 逐条对照目标清单与组件清单。今天发现「静态知识 × 动态数据融合问答」是四项立项能力之一，而所有子图要么纯检索、要么纯 SQL——该能力交付时拿不出证据。

### 第 2 层：状态机与编排

- [ ] **框架的执行语义查了吗？** 中断恢复是「从挂起点继续」还是「重跑整个节点」？后者意味着 interrupt 之前的所有副作用都会重复执行——令牌被重新生成、审计行重复、上游节点可能得出不同结论。**这是文档读起来最像、实际最不像的地方。**
- [ ] **一次性令牌有持久化落点和唯一约束吗？** 光有「一次性」的文字承诺，没有落库位置、没有 UNIQUE 约束、没有 TTL、用「先查后写」消费——并发下必然重复执行。
- [ ] **中断有超时吗？** 多数编排框架的人工中断是无限期等待。三天前的确认卡片今天点下去照样恢复，而前置校验早已失效。
- [ ] **必填槽位数与追问轮次上限相容吗？** 9 个必填槽位、逐个追问、上限 3 轮——算术上填不完。而写操作的超限兜底不能是「用已知条件给最佳结果」。
- [ ] **拒绝/取消后状态怎么回退？** 用户拒绝往往是「填错了想改」而非「不做了」。
- [ ] **路由决策的依赖有环吗？** 「网关按请求类型分流」而「类型判断依赖尚未发生的意图识别」——循环依赖。
- [ ] **粘性/缓存机制与切换检测互斥吗？** 「意图未变则跳过重新识别」+「切换时保留快照支持回切」——粘性一旦生效，切换事件永远检测不到。

### 第 3 层：数据模型

- [ ] **自然语言里的名词能落到 code 上吗？** 表里只有 `product_code` 没有 `product_name`，用户说「白色岩板的库存」时这个映射不存在。
- [ ] **声称的「真实计算逻辑」真的会被执行吗？** 字段存在 ≠ 参与运算。若结果字段已是给定值，中间参数就是死字段。
- [ ] **关联的粒度对吗？** 计划关联到订单头而非订单行，一单多行时无法判断哪条计划服务哪一行。
- [ ] **幂等键有落库位置和唯一约束吗？** 唯一索引仲裁竞态，应用层「先查后写」不行。
- [ ] **审计记录的是「工具调用出入参」还是「业务记录的状态迁移」？** 前者答不出「谁把这单从 X 改到 Y」。
- [ ] **审计写与业务写的事务边界定了吗？** 同事务 → 失败的写尝试无痕；分离事务 → 有窗口。两段式（attempt 行 → 执行 → outcome 行）通常是对的。
- [ ] **「不可篡改」是应用层自律还是数据库强制？** `REVOKE UPDATE, DELETE` 一行 SQL 就是 90%。
- [ ] **数据分布规格化了吗？** 「每表 ≥100 条」不等于「关键形态都有样本」。均匀随机生成通常产不出边界用例需要的联合分布。

### 第 4 层：安全

- [ ] **不可信输入与写能力在同一个上下文里吗？** 用户自然语言 + 检索到的文档内容都会进 LLM 上下文，而 LLM 能调写操作 API。
- [ ] **「二次确认」防的是模型犯错还是模型被操纵？** 结构上完全合法的确认卡片，人不会逐字符核对。二次确认不是注入的兜底。
- [ ] **最便宜的缓解是什么？** 通常是一条不变量声明：**写子图不摄入任何检索文本，写载荷只来自对话槽位与用户确认过的卡片。** 利用现有拓扑，不增加架构。
- [ ] **令牌会进入模型上下文吗？** 若会，注入可诱导模型自我确认。
- [ ] **数据范围过滤器由谁填？** 若由模型依据用户措辞填充，它既不是权限控制也是注入靶点。**必须服务端按身份注入。**
- [ ] **外泄通道盘点了吗？** 通知渠道、引用原文渲染、任何模型可触达的出站请求。

### 第 5 层：环境与资源

- [ ] **资源核算表与组件清单对得上吗？** 部署拓扑里列了的组件，核算表里有对应行吗？今天漏了 embedding/rerank 约 3–4GB。
- [ ] **宿主基线算了吗？** 操作系统、容器运行时的 VM、开发者本来就开着的浏览器和编辑器。
- [ ] **「精简部署」在当前版本真的可行吗？** 去查该版本的实际服务清单——文档里假设「不启用某组件」，而该组件在新版本里没有开关。
- [ ] **默认配置是字面量还是插值派生的？** 「从列表里移除某项」的处置，遇到插值派生的配置会静默失效——设了上游变量它自动回来了。
- [ ] **有备份方案吗？** 权威数据在开发机上、审计不可丢，而全文档没有备份动作。比磁盘故障现实得多的杀手是 `down -v`。
- [ ] **演示日的串联依赖有多长？有降级预案吗？** 数一遍：几个服务必须同时健康？其中几个依赖第三方？
- [ ] **可观测性的最小口子留了吗？** 要出延迟和并发结论，就需要首 token、token 数、各阶段耗时的埋点。**这些字段必须在数据产生之前定，事后加是迁移 + 重跑。**

### 第 6 层：估算与交付

- [ ] **估算是自下而上还是自上而下？** 判据很简单：**看它的修订史。如果每次变动都是「补记漏项」且只单向上调，那就是拍的。**
- [ ] **估算工具排在什么时候产出？** 任务级 WBS 被列为最后阶段的交付物，等于本该用来估算的工具排在估算之后。
- [ ] **人天与日历日混淆了吗？** 「N 人天 ÷ 5 天/周」隐含 100% 投入效率。单人项目计入沟通、环境折腾、上下文切换后，现实通常是每周 3.5–4 有效人天。
- [ ] **前置的是哪个风险？** 常见错误：前置了**退路便宜**的风险，把**二元、无退路、补救手段全在上游**的风险留到最后。前置的判据是「失败后补救成本」，不是「技术上不确定」。
- [ ] **缓冲的量、位置、动用规则？** 均匀铺开的缓冲对集中在某两个阶段的方差无效；没有动用规则的缓冲会在进度压力下被静默吃掉。
- [ ] **交付物集中在最后阶段吗？** 那个阶段同时承接前面所有延误，风险画像是倒置的。文档随阶段增量写通常几乎不增加总量。
- [ ] **报告能支撑它存在的决策吗？** 逐条列出决策需要回答的问题，对照本次能产出的证据。常见缺口：成本维度只有本次试验的花费，没有规模化的 TCO 模型。

### 第 7 层：文档自洽

- [ ] **跨章节语义一致吗？** 机械自查（占位符、算术、编号）抓不到语义矛盾。今天两处都是这么漏的：一处是同一组件在两章里归属不同，一处是基准文档与设计文档对同一接口的要求相反。
- [ ] **作为核对基准的文档，自己漂移了吗？** 若「宪法/规范」与设计文档矛盾，以它为基准的检查机制就是空转——按哪份查都能得出相反结论。
- [ ] **版本号交叉引用对得上吗？** 三份文档互相引用三个不同版本号，是漂移已经发生的直接证据。
- [ ] **枚举值在各处一致吗？** DDL 注释列了三个值，正文用了第四个。
- [ ] **有未赋值的占位符吗？** 「超时（>N 秒）」的 N 始终没填。

## 四、评审者自身的推理陷阱

这些是今天在**我自己的设计**里发现的，不是评审者发现的：

- **推翻一条论据 ≠ 换结论。** 一个选型有四条理由，发现其中一条不成立，正确做法是重审其余三条，而不是直接改选另一个方案。今天的向量库选型因此绕了一整圈又绕回来。
- **约束要用在它成立的地方。** 「本机内存不够」这条约束被用在了一个部署在**另一台机器**上的组件上。
- **新证据到达时要重算派生决策。** 「GPU 改用租用实例」这个变更，连带使「权威数据库放 GPU 服务器」不再成立——按小时计费、可随时释放的实例不能承载权威数据。派生决策不会自己更新。
- **收益要诚实计价。** 「换用新版本」的收益如果只是「支持周期多一年」，就要问这一年值不值两个待验证的未知项压在关键路径上。

## 五、汇总报告结构

```
## 一、总体结论（方向对不对 / 问题集中在哪几层）
## 二、交叉收敛矩阵（问题 × 独立指出人数，按人数降序）
## 三、阻塞项（按层归并，每条含处置与代价）
## 四、汇总人裁决：驳回与下调（含驳回依据）
## 五、需要决策者拍板的事项
## 六、专家一致肯定的（保留这些，改动时不要误伤）
## 七、专家自陈的不确定项（不可当作结论使用）
```

第四节和第七节是这个结构区别于「问题清单」的地方：**它明确区分了「已验证的结论」「被驳回的结论」「未验证的推断」三类，让读者知道每条该用多大力气对待。**
