# 架构评审要点结构

## 为什么这件事的收益如此不对称

同一个缺陷，在三个时点的修复成本差着数量级：

| 时点 | 典型成本 | 例 |
|---|---|---|
| 设计评审时 | 改几行文档 | 把副作用拆成中断前的独立节点 |
| 实施中途 | 重写一个模块 | 下单子图已写完，拓扑要推倒 |
| 验收时 | 重造数据 + 重跑全部评测 | 表结构要改，模拟数据与用例全部作废 |

所以评审的目标不是"找到最多的问题"，而是**找到那些会在中途爆炸、且补救手段已在上游的问题**。一条只影响局部的缺陷可以留到实施时发现；一条改变数据模型或状态机拓扑的缺陷必须现在发现。

这个不对称也决定了严重度的判据（见下）。

## 一、组织评审

### 视角必须互不重叠

评审的信号来自**独立视角的收敛**。若三位评审者视角高度重合，他们指出同一问题不构成额外证据——那是回声。切分时让每个视角有自己的**专业判据来源**，而不是按模块切：

| 视角 | 独有判据来源 |
|---|---|
| 领域实现 | 该技术栈的实际能力边界与已知陷阱 |
| 状态与编排 | 框架的执行语义（重放、检查点、中断恢复、事务） |
| 数据与后端 | 数据模型能否支撑业务推理；幂等与事务边界 |
| 环境与运维 | 资源核算、部署拓扑、可观测性、演示日风险 |
| 安全与合规 | 攻击面、审计完备性、权限模型 |
| 交付管理 | 估算方法、指标可证伪性、决策转化 |

六个是较完整的覆盖。人手不足时优先保留**状态与编排 + 数据 + 交付管理**——今天的阻塞项密度在这三处最高。

**今天没有覆盖、但在别的项目里应当加上的视角**：可测试性与测试策略、数据迁移与回滚路径、供应商锁定与许可证合规、团队能力匹配、国际化与本地化、无障碍。判断是否需要：**该维度出问题时，补救成本是否也在上游？**

### 并行派发，互不知情

同一条消息里发出全部派发，让它们并行且互相看不到结论。派发后放后台，不要阻塞等待。

派发指令必须**自包含**——评审者冷启动，不共享你的上下文。每份都要带：项目背景、技术选型、硬约束（人数/预算/工期）、待评审文件的**绝对路径**、该视角的专属审查点、输出格式。

模板见 `references/reviewer-prompts.md`。

### 四条防注水约束（缺一条就会漂移）

不给约束，评审者会系统性地朝三个方向漂移：凑数、按生产标准苛求、无限加需求。

1. **「不要为凑数编造问题。某部分确实没问题就直接说没问题。」**
2. **「这是 <PoC / MVP / 内部工具>，不是生产系统，不要用生产级标准苛求。」** 并说明例外——通常是审计与安全红线，因为那是立项时的硬承诺。
3. **「团队 N 人、预算 M。任何『建议增加 XX』必须评估工作量代价并说明拿什么换。」**
4. **「凡涉及具体 API 能力、字段、版本行为，实际查证源码或官方文档，不要凭记忆断言；查不到就写进『我不确定的地方』，不要反复重试。」**

第 4 条的后半句有实际原因：**反复重试外部查证是评审 agent 掉线的主要原因**。限制查证次数比允许无限查证更可靠。

### 强制的输出结构

```
## 总体判断（一到两句）
## 发现（按 阻塞 > 重要 > 建议 排序）
   每条：位置 / 问题 / 依据（技术依据，非空泛）/ 建议（含代价）
## 做得对的地方（简短，不要客套）
## 我不确定的地方
```

**「我不确定的地方」是整个结构里最有价值的一节。** 它把"查证过的结论"与"基于经验的推断"分开，直接决定汇总时哪些可直接采纳、哪些必须自己复核。没有这一节，两者混在一起无法区分，而混在一起的代价是你要么全信（会被错误结论带偏）要么全查（评审就白做了）。

### 严重度校准（评审者常用得不一致，派发时就写明）

| 级别 | 判据 |
|---|---|
| **阻塞** | 会导致**架构级返工或验收失败**，且**补救手段在上游** |
| **重要** | 会导致局部返工、指标失真或结论不可用，但补救手段仍在当前或下游阶段 |
| **建议** | 改善质量，不改变结论、不造成返工 |

关键在"补救手段在哪里"。一个很严重但随时能改的问题，不是阻塞；一个看起来温和但改起来要动数据模型的问题，是阻塞。

## 二、汇总裁决

**汇总者的职责是裁决，不是传话。** 一条引用了具体文件路径和 issue 编号的结论，仍然可能是错的——今天约五十条发现里驳回了两条，两条都会造成实际损害。

### 必须自己验证的三类结论

| 类别 | 为什么 |
|---|---|
| 会导致**架构改动或返工**的阻塞项 | 错误的阻塞项让你付出不必要的工期与复杂度 |
| 与**已有实测证据冲突**的结论 | 评审者的信息可能比你旧 |
| 断言**「某能力不存在」**的 | 这类最容易错 |

第三类有个具体失败模式值得单独记住：评审者查了某 API 的顶层参数列表，没找到目标字段，就断言"不支持"。实际该字段嵌在其中一个**参数对象的内部**，是一等公民。**「我在这一层没看到」不等于「它不存在」——多往下看一层。**

### 部分正确怎么处理

今天那条驳回是"观察对、结论错"：顶层参数确实没有该字段（观察成立），但据此推出"不支持、须绕道 workflow"（结论不成立）。

处理方式是**分开裁决**：保留观察、驳回结论、说明分歧点。直接整条驳回会丢掉有效信息；整条采纳会付出 0.5 人天和一层多余架构。

同类还有"夸大"——今天有条说"两个命名都还在用"，实测其中一个只出现在修订记录里（那是历史记录应有的样子）。处理方式是**下调而非驳回**：指出夸大，保留其核心论点（该接口的命名与契约层次确实错位）。

### 证据时效性优先于评审结论

评审期间若出现新实测证据（用户跑通了某组合、某版本发布了），**证据推翻结论**。明确写明该评审者写作时不掌握这一信息，再驳回——这不是否定评审者，是记录裁决依据。

### 收敛计数：用于排序，不用于筛选

把发现**归一化为同一句问题陈述后**再计数——不同评审者用不同词汇描述同一缺陷（"令牌无唯一约束"/"幂等键无落库位置"/"确认可被重放"其实是同一件事的三个切面）。不归一化就统计，会低估收敛度。

**收敛数高 = 多个专业视角同时验证，优先处理。但收敛数不等于重要性。** 今天最有价值的一条发现只有一位评审者指出——因为只有他去查了框架的执行语义文档。

## 三、二十种缺陷原型

这是本技能的核心。完整版含真实实例、检查方法与修复模式见 **`references/defect-archetypes.md`**。

| # | 原型 | 一句话识别 |
|---|---|---|
| A1 | **承诺-机制缺口** | 文档承诺了性质（一次性/不可篡改/幂等/不可回溯），但没有任何机制实现它 |
| A2 | **框架语义假设** | 按直觉语义排列流程，而框架的实际执行语义不同 |
| A3 | **双路皆堵** | 写"A 或 B"看似灵活，A 被本文档别处约束堵死，B 被方法论约束堵死 |
| A4 | **循环决策依赖** | X 的决策需要 Y 的结果，而 Y 在 X 之后发生 |
| A5 | **算术不相容** | 两个数量约束乘起来就不成立 |
| A6 | **死字段** | 字段存在但无计算路径消费它，其存在被当作能力的证据 |
| A7 | **指标无对象** | 验收指标要测的东西在设计里不存在 |
| A8 | **指标无谓词** | 有数字没有判定规则，因而不可证伪 |
| A9 | **核算漏项** | 资源/工期核算表与组件/任务清单对不上 |
| A10 | **默认配置陷阱** | 处置方式基于对配置机制的错误理解 |
| A11 | **约束错位** | 把约束用在它不成立的地方 |
| A12 | **派生决策未重算** | 上游决策变了，依赖它的下游决策没跟着重算 |
| A13 | **论据部分推翻即换结论** | 多理由支撑的结论，推翻一条就换方案，不重审其余 |
| A14 | **基准自相矛盾** | 用作核对基准的文档与主文档矛盾，检查机制空转 |
| A15 | **目标无落点** | 立项目标在架构里找不到承接组件 |
| A16 | **不可信输入与特权同域** | 不可信文本与写能力共享同一上下文 |
| A17 | **交付倒置** | 高风险产出集中在最后阶段，同时承接前面所有延误 |
| A18 | **前置错风险** | 前置了有便宜退路的，留下二元无退路的 |
| A19 | **自评闭环** | 同一人写题、答题、判卷、写结论 |
| A20 | **单位缺失** | 数量字段无单位，跨表比较时不可比 |

**扫描顺序建议**：A7/A8/A15（需求层，最贵）→ A1/A2/A3/A4/A5（机制层）→ A6/A20（数据层）→ A16（安全）→ A9/A10/A11（环境）→ A17/A18/A19（交付）→ A12/A13/A14（文档演化）。

## 四、七层要点清单

逐条含触发场景与检查手法，见 **`references/seven-layer-checklist.md`**。

1. **需求与验收**——指标有谓词吗？有可测对象吗？样本量能表达精度吗？谁出题谁判卷？
2. **状态机与编排**——框架执行语义查了吗？令牌有落点和唯一约束吗？中断有超时吗？槽位数与轮次上限相容吗？
3. **数据模型**——自然语言能落到 code 吗？声称的计算逻辑真会执行吗？关联粒度对吗？审计记的是出入参还是状态迁移？
4. **安全**——不可信输入与写能力同域吗？二次确认防的是犯错还是被操纵？过滤器由谁填？
5. **环境与资源**——核算表与组件清单对得上吗？宿主基线算了吗？有备份吗？演示日串联依赖多长？
6. **估算与交付**——自下而上还是自上而下？人天与日历日混淆了吗？前置的是哪个风险？
7. **文档自洽**——跨章节语义一致吗？基准文档自己漂移了吗？

## 五、查证手法

评审质量的下限由查证能力决定。版本、API 能力、生命周期这三类断言**永远不要凭记忆**——它们变得快，且错了代价高。

具体的 registry API、命令、以及今天踩到的四个坑（macOS 上 Python 缺 CA 证书、wheel 标签检测漏 ABI 无关轮子、只发 tag 不发 Release 的项目、动态渲染的厂商文档），见 **`references/verification-toolkit.md`**。

文档自洽的机械检查（版本漂移、枚举不一致、未赋值占位符、交叉引用失效）也在同一份参考里，可直接复制运行。

## 六、评审者的七种失败模式

派发前知道这些，能在读结论时校准信任度：

| # | 失败模式 | 表现 |
|---|---|---|
| R1 | 只看一层就断言不存在 | 顶层参数没有 → "不支持" |
| R2 | 把观察当结论 | 观察成立，但推论跨了一步没验证 |
| R3 | 夸大普遍性 | "到处都是"实际只有一两处，且其中一处是合理的 |
| R4 | 用生产标准苛求 | 给 PoC 提 WORM 存储、完整 RBAC、Prometheus 全家桶 |
| R5 | 建议增加而不评估代价 | 每条建议都对，加起来把工期翻倍 |
| R6 | 信息过期 | 不掌握你刚拿到的实测证据 |
| R7 | 无限重试外部查证 | 导致超时掉线，评审白做 |

R4 和 R5 靠派发指令的约束防；R1/R2/R3 靠汇总时的自主验证防；R6 靠你自己掌握最新证据；R7 靠指令里明确"查不到就写进不确定"。

## 七、汇总报告结构

```
## 一、总体结论（方向对不对 / 问题集中在哪几层）
## 二、交叉收敛矩阵（归一化后的问题 × 独立指出人数，降序）
## 三、阻塞项（按层归并，每条含处置与代价）
## 四、汇总人裁决：驳回与下调（含驳回依据）
## 五、需要决策者拍板的事项
## 六、专家一致肯定的（保留这些，改动时不要误伤）
## 七、专家自陈的不确定项（不可当作结论使用）
```

第四、六、七节是这个结构区别于"问题清单"的地方。它明确区分了**已验证的结论 / 被驳回的结论 / 未验证的推断 / 不要动的部分**四类，让读者知道每条该用多大力气对待——也让下一个接手的人不会把某条推断当成定论去执行。

第六节尤其容易被省略，但它有实际作用：**大改之后，被肯定的那些设计最容易被顺手改坏。**

## 八、评审者自身的推理陷阱

以下四条来自今天在**被评审的设计**里发现的，而那份设计是我自己写的。它们不属于评审技巧，属于设计时就该避免的：

- **推翻一条论据 ≠ 换结论。** 一个选型有四条理由，发现其中一条不成立，正确做法是重审其余三条。今天的向量库选型因此绕了一整圈又回到原点。
- **约束要用在它成立的地方。** "本机内存不够"被用在了部署于**另一台机器**的组件上。
- **新证据到达时要重算派生决策。** "GPU 改用租用实例"连带使"权威数据库放 GPU 服务器"不再成立——按小时计费、可随时释放的实例不能承载权威数据。派生决策不会自己更新。
- **收益要诚实计价。** "换新版本"的收益若只是"支持周期多一年"，就要问值不值两个未验证组合压在关键路径上。
