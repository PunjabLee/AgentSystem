# 七层要点清单

每条格式：**检查项 → 为什么 → 怎么查**。括号内是对应的缺陷原型（见 `defect-archetypes.md`）。

---

## 第 1 层 · 需求与验收

最常被跳过，返工最贵——因为它的补救手段全在上游。

- [ ] **每条验收指标有判定谓词吗？**（A8）无判定规则的数字不可证伪。逐条问：谁来判 / 按什么规则判 / 判错了怎么发现。
- [ ] **每条验收指标有可测试的对象吗？**（A7）测试集与组件清单**双向映射**，两个方向的空缺都要解释。
- [ ] **样本量能表达指标的精度吗？** 每场景 6 条 = 16.7 个百分点的分辨率，"≥90%"在单场景层面无法表达。n=40 时 90% 的 95% 置信区间约 76%–97%。**用于比较两个方案时，n=40 大约只能检出 15–20 个百分点以上的差距。**
- [ ] **谁出题、谁判卷？**（A19）同一人占了几环？最便宜的解药是让需求方用自己的话出 10–15 条题。
- [ ] **单次运行还是多次？** 没有固定温度与随机种子的单次运行，**运行间方差与被比较的差异完全混淆**。
- [ ] **立项目标在架构里都有落点吗？**（A15）逐条对照目标清单与组件清单。
- [ ] **报告能支撑它存在的那个决策吗？** 列出决策需要回答的问题，对照本次能产出的证据。常见缺口：成本维度只有本次试验花费，没有规模化的 TCO 模型——而成本往往是**唯一真正驱动决策**的维度。
- [ ] **有没有维度已经作废了？** 若某个对比维度因环境限制拿不到实测证据，**现在就声明**，别让它在报告里以模糊结论的形式存在。

## 第 2 层 · 状态机与编排

- [ ] **框架的执行语义查了吗？**（A2）中断、恢复、重试、重放、事务、并发——这六个词出现处都是高危区。搜 `re-run` / `replay` / `idempotent` / `checkpoint boundary`。
- [ ] **一次性令牌有持久化落点和唯一约束吗？**（A1）文字承诺 + "先查后写"消费，并发下必然重复执行。
- [ ] **中断有超时吗？** 多数编排框架的人工中断**无限期等待**。三天前的确认卡片今天点下去照样恢复，而前置校验早已失效。
- [ ] **必填槽位数 × 追问轮次上限，算得过来吗？**（A5）且写操作的超限兜底不能是"用已知条件给最佳结果"。
- [ ] **拒绝 / 取消后状态怎么回退？** 用户拒绝往往是"填错了想改"而非"不做了"。回退到槽位填充节点、作废旧令牌、允许改单，而不是清空会话。
- [ ] **同意图内的槽位修正处理了吗？** "刚才说优等品，改成一级品"——比切换意图更常见，且模型容易把新值当作新增槽位而非覆盖。
- [ ] **路由决策的依赖有环吗？**（A4）画请求路径，每个决策点标注需要什么信息、该信息何时产生。
- [ ] **粘性 / 缓存机制与切换检测互斥吗？** "意图未变则跳过识别" + "切换时保留快照支持回切"——粘性一旦生效，切换事件永远检测不到。解法是让最廉价的那一级**永远跑**。
- [ ] **分类 / 路由的"覆盖率"是命中率还是准确率？** 命中即短路的规则层，错了没有任何环节纠正。**误判代价高的意图（尤其写操作）不应由规则层直接路由。**
- [ ] **多级 fallback 的判据是什么？** 缺判据不只是"少写一句话"——它反过来约束上一级的技术形态（能给出连续置信度的方案 vs 只能输出标签的方案）。
- [ ] **两套编排系统的职责边界，判据与分配一致吗？** 若文档自己列了归属判据，逐条套一遍。命中判据却分给了另一侧的，要么改分配，要么写明例外理由。
- [ ] **降级路径比正常路径跨了更多系统吗？** 故障时还得指望更多组件在线，方向就是反的。

## 第 3 层 · 数据模型

- [ ] **自然语言里的名词能落到 code 上吗？** 表里只有 `product_code` 没有 `product_name`，用户说"白色岩板的库存"时这个映射不存在。若要求先检索出 code 再查 SQL，等于把检索误差引入了本该确定的查询路径。
- [ ] **声称的"真实计算逻辑"真的会被执行吗？**（A6）字段存在 ≠ 参与运算。
- [ ] **关联的粒度对吗？** 计划关联到订单头而非订单行，一单多行时算不出行级结论。
- [ ] **所有数量字段有单位吗？**（A20）
- [ ] **幂等键有落库位置和唯一约束吗？**（A1）唯一索引仲裁竞态，应用层"先查后写"不行。
- [ ] **审计记的是"工具调用出入参"还是"业务记录的状态迁移"？** 前者答不出"谁把这单从 X 改到 Y"——入参是 `{order_no, new_status}`，旧值无处留存。
- [ ] **审计写与业务写的事务边界定了吗？** 同事务 → 失败的写尝试无痕（而这恰是审计最关心的一类事件）；分离事务 → 有"业务已提交、审计未落"的窗口。**两段式**（独立连接先写 attempt 行 → 业务事务提交/回滚 → 追加 outcome 行，同 trace_id 串联）通常是对的，且天然满足"仅追加"。
- [ ] **"不可篡改"是应用层自律还是数据库强制？**（A1）`REVOKE UPDATE, DELETE` 一行 SQL 就是 90%。
- [ ] **数据分布规格化了吗？** "每表 ≥100 条"不等于"关键形态都有样本"。均匀随机生成通常产不出边界用例需要的**联合分布**——算一遍：100 行库存要让每个 (产品, 色号) 平均有 3 个批次，产品目录就必须压到十几个 SKU。交付一份 fixture 规格（把每条用例映射到它依赖的数据条件）+ 固定随机种子 + 生成后断言校验。
- [ ] **跨库还是跨 schema？** "同实例"不等于"同库"——PostgreSQL 不能跨 database JOIN，需要 `postgres_fdw`。若某个选型理由是"可以直接 join 对账"，先确认布局。
- [ ] **权限授予会静默漏掉后建的表吗？** `GRANT ... ON ALL TABLES` 只对执行那一刻已存在的表生效。迁移建的表、懒创建的表都会漏，而开发者遇到 permission denied 后最省事的"修复"就是放宽权限，红线随即被架空。需要 `ALTER DEFAULT PRIVILEGES FOR ROLE <将来实际建表的角色>`。

## 第 4 层 · 安全

- [ ] **不可信输入与写能力在同一个上下文里吗？**（A16）
- [ ] **不可信文本的来源盘点全了吗？** 用户输入是显而易见的一条；**检索到的文档内容**是更严重的一条，尤其当知识库允许业务人员自助上传时。
- [ ] **"二次确认"防的是模型犯错还是模型被操纵？** 结构上完全合法的确认卡片，人不会逐字符核对。
- [ ] **确认令牌会进入模型上下文吗？** 若会，注入可诱导模型自我确认，人类根本没被询问过。
- [ ] **恢复执行时用的是"确认时展示的那份载荷"还是"重新由模型产出的"？** 后者是 TOCTOU 窗口——用户核对的卡片与实际提交的不是同一个对象。
- [ ] **数据范围过滤器由谁填？** 若由模型依据用户措辞填充，它既不是权限控制（用户直接说"查另一个部门的"即可越权），也是注入靶点。**必须服务端按身份注入。**
- [ ] **外泄通道盘点了吗？** 通知渠道、引用原文渲染、任何模型可触达的出站请求。webhook 目标必须固定在配置里，不取自模型输出。
- [ ] **审计能防篡改吗？失败的操作记不记？被拒绝的确认记不记？**
- [ ] **跨系统操作的两侧日志能 join 吗？** RPA / 集成场景下对端只看到一个服务账号，合规举证需要把本侧 `trace_id` 写进对端的可见字段。
- [ ] **取证产物会拍到凭据吗？** 截图取证会把密码框、URL 里的 token 一并拍进去。
- [ ] **"审计要求"来自哪个主体？** 内控 / 监管 / 客户审厂，对必备字段、留存年限、完整性强度的要求差异很大。不确定就问一次，它决定规模化时审计模块要重做多少。

## 第 5 层 · 环境与资源

- [ ] **资源核算表与组件清单对得上吗？**（A9）
- [ ] **宿主基线算了吗？** 操作系统、容器运行时的 VM、开发者本来就开着的浏览器和编辑器。
- [ ] **"精简部署"在当前版本真的可行吗？** 去查该版本的**实际服务清单**——文档假设"不启用某组件"，而该组件在新版本里可能没有开关。
- [ ] **默认并发/worker 数是多少？** 文档常假设"单 worker"，而默认值可能是 4。
- [ ] **默认配置是字面量还是插值派生的？**（A10）
- [ ] **有备份方案吗？** 权威数据在开发机上、审计不可丢，而全文档没有备份动作。比磁盘故障现实得多的杀手是 `docker compose down -v`。**没恢复演练过的备份不算备份。**
- [ ] **最贵的产出是什么？它在备份范围内吗？** 通常不是代码，是人工标注、调过的参数、写好的语料。
- [ ] **演示日的串联依赖有多长？** 数一遍：几个服务必须同时健康？其中几个依赖第三方（含算力平台库存）？**演示默认档位应选依赖最短的那条链。**
- [ ] **有降级预案吗？** 一条 `make demo-check` 探测全链路 + 关键场景录屏兜底。
- [ ] **"失败降级"定义到哪一档了？** 只写"支持降级"而不写降级到哪，等于没写。
- [ ] **可观测性的最小口子留了吗？** 要出延迟和并发结论，就需要首 token、token 数、各阶段耗时的埋点。**这些字段必须在数据产生之前定，事后加是迁移 + 重跑。** 但不要为此搭监控全家桶——日志 + SQL 查询 + 服务端 `/metrics` 快照通常够用。
- [ ] **CI 跑什么？在哪跑？** 若 CI 需要本地大模型，会与"错峰运行"之类的约束互斥。**把 CI 收敛为不含模型调用的部分**（lint、类型、单测、以及基准文档的机械检查），通常是减工作量而非增加。
- [ ] **按需启停的真实成本算过吗？** 权重加载、首次下载、隧道重建、健康检查——每次"开机到可用"的分钟数 × 预计次数。

## 第 6 层 · 估算与交付

- [ ] **估算是自下而上还是自上而下？** 判据：**看修订史。每次变动都是"补记漏项"且只单向上调，就是拍的。**
- [ ] **估算工具排在什么时候产出？** 任务级 WBS 若被列为最后阶段交付物，本该用来估算的工具排在了估算之后。
- [ ] **人天与日历日混淆了吗？** "N 人天 ÷ 5 天/周"隐含 100% 投入。单人项目现实通常是每周 3.5–4 有效人天。
- [ ] **前置的是哪个风险？**（A18）判据是"失败后补救成本"，不是"技术上有多不确定"。
- [ ] **缓冲的量、位置、动用规则？** 均匀铺开的缓冲对集中在某两阶段的方差无效；没有动用规则的缓冲会在进度压力下被静默吃掉。**集中持有 + 日历决策门。**
- [ ] **交付物集中在最后阶段吗？**（A17）
- [ ] **砍范围清单准备好了吗？** 按"决策价值 / 成本"排序，并明确标出**不可砍**的部分。临场决定砍什么，砍的往往是最不该砍的。
- [ ] **外部依赖有清单吗？** API Key、账号、凭据、第三方审批——每项标注负责人与最晚到位时间。单人项目里这类阻塞最容易被忽略。

## 第 7 层 · 文档自洽

- [ ] **跨章节语义一致吗？**（A14）机械自查抓不到这类矛盾，必须显式列出跨章节引用的概念逐一核对：组件归属、接口契约、数据流向、职责边界。
- [ ] **作为核对基准的文档，自己漂移了吗？** 若基准与主文档矛盾，以它为基准的检查机制就是空转。**把"基准与主文档版本一致"列为每次收敛检查的第一项。**
- [ ] **基准条文的"如何验证"可机械执行吗？** 需要人判断的条文进不了 CI，进不了 CI 就会漂移。
- [ ] **版本号交叉引用对得上吗？** 三份文档互相引用三个不同版本号，是漂移已发生的直接证据。
- [ ] **枚举值在各处一致吗？** DDL 注释列了三个值，正文用了第四个。
- [ ] **有未赋值的占位符吗？** "超时（>N 秒）"的 N 始终没填。
- [ ] **架构图与正文一致吗？** **图是被读得最多的东西**，改了正文没改图，实现者照图做。
- [ ] **风险登记册的编号连续吗？** 乱序会让"逐条核对"这种使用方式失效。
