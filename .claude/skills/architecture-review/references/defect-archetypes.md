# 二十种缺陷原型

每条含：**识别特征 → 真实实例 → 检查手法 → 修复模式**。
实例全部来自一次企业级 AI PoC 架构评审（LangGraph + Dify + PostgreSQL + vLLM，单人 8 周）。

---

## 机制层

### A1 承诺-机制缺口

**识别**：文档承诺了某个性质，但全文找不到实现它的机制。承诺用形容词表达，机制需要 DDL、GRANT、索引或代码。

**实例**
| 承诺 | 实际 |
|---|---|
| 「`confirm_token` 一次性，重复提交返回原结果」 | 无落库位置、无 UNIQUE 约束、无 TTL，靠应用层"先查后写" |
| 「审计表仅追加不更新、不提供删除接口」 | 应用账号是表属主，一条 `DELETE` 照走 |
| 「脱敏结果不可回溯到真实主体」 | 格式保留化名，保留了区域+业态两个真实属性，属假名化而非匿名化 |

**检查手法**：全文搜索性质形容词——`一次性 / 唯一 / 原子 / 不可 / 必须 / 保证 / 幂等 / 不得`。对每一处问：**哪一行 DDL、哪一条 GRANT、哪一个索引实现它？** 答不出就是缺口。

**修复模式**：把性质下沉到数据库层。唯一性 → UNIQUE 约束 + `INSERT ... ON CONFLICT`；不可篡改 → `REVOKE UPDATE, DELETE` + 触发器；原子消费 → `UPDATE ... WHERE state='pending' RETURNING` 判 rowcount，而非先查后写。

### A2 框架语义假设

**识别**：设计按"名字听起来的语义"排列流程，而框架的实际执行语义不同。中断、恢复、重试、重放、事务、并发这六个词出现的地方，都是高危区。

**实例**：设计把「库存校验 → 生成一次性令牌 → 生成确认卡片」三个副作用**全放在 `interrupt()` 之前的同一个节点内**，流程图读起来像"从挂起点继续"。

LangGraph 官方文档原文：*"Because interrupts work by re-running the nodes they were called from, side effects called before interrupt should (ideally) be idempotent."* ——**恢复是重跑整个节点**。

三个后果，每个都独立致命：
1. 令牌**被重新生成**，用户手上卡片的令牌对不上，一次性校验失效
2. 审计埋点在同节点内 → **重复审计行**，而"仅追加不更新"使重复行无法收敛
3. 上游调度节点也从头重跑 → **可能重新做一次意图识别并得出不同结论**

**检查手法**：凡涉及那六个词的设计，去读框架文档的**执行语义原文**，不要按名字推断。搜索关键词：`re-run` / `replay` / `idempotent` / `at-least-once` / `checkpoint boundary`。

**修复模式**：把副作用拆成中断**之前**的独立节点——节点边界即检查点边界，已完成的节点不会被重放。中断所在节点做到零副作用。顺带利用重放：把前置校验放在会被重放的位置，恢复时自动获得最新状态。

### A3 双路皆堵

**识别**：设计写"A 或 B"，看起来是留了灵活性，实际两条都走不通——A 被**本文档别处的硬约束**堵死，B 被**方法论约束**堵死。因为写的是"或"，读的时候会自动假设至少有一条可行。

**实例**：三级意图路由的 L2 层写「用 M0 档 Qwen3-8B **或** embedding + 分类头」。
- Qwen3-8B 路线：撞上同一文档 §5.2 的硬约束「Ollama 与 Dify 不得同时运行，须错峰」。而 L2 要在每个请求上跑，检索又走 Dify——一次请求同时需要两者在线。
- embedding + 分类头路线：需要标注数据。全项目唯一的标注数据是验收评测集，**拿它训分类器 = 训练集测试集同源**，两个验收指标同时失效。

**检查手法**：每处"或"、"二选一"、"可以……也可以"，对**两个选项分别**做全文约束检索。别只验证你偏好的那个。

**修复模式**：找第三条路。本例的解是**零训练 embedding 最近邻**——每意图手写 8–15 条原型话术，编码成 centroid，线上算 cosine，top1/top2 的 margin 天然就是置信度。零标注、零训练、不新增进程、不触发互斥，且顺带解决了"三级之间 fallback 判据缺失"这个独立问题。**比原方案更便宜。**

---

### A4 循环决策依赖

**识别**：X 处的决策需要 Y 的结果，而 Y 在 X 之后才发生。常见于分层架构里"上层做路由、下层做识别"。

**实例**：网关按"无状态纯知识问答 vs 有状态请求"分流，但**判断请求属于哪一类本身就是意图识别**，而意图识别住在网关之后的 Supervisor 里。且两类请求语料同源、关键词空间重叠，网关无从分辨。

**检查手法**：画一遍完整请求路径，在每个决策点标注：**这个决策需要什么信息？该信息在哪一步产生？** 箭头指回上游就是环。

**修复模式**：要么把决策下移到信息产生之后，要么让上层复用一份**保守的、不需要完整信息的规则**——本例的解是"仅当无活跃会话 且 命中纯知识关键词白名单才直通，其余一律走全链路"，复用同一份 L1 规则表，不引入第四套判据。

---

### A5 算术不相容

**识别**：两个数量约束单看都合理，乘起来就不成立。文档很少把它们写在一起，所以需要主动列表验算。

**实例二则**
| 约束 A | 约束 B | 冲突 |
|---|---|---|
| 写操作有 9 个必填槽位 | 「逐个追问，上限 3 轮」 | 首轮填 2–4 个已属乐观，剩余 5–7 个填不完。而写操作的超限兜底不能是"用已知条件给最佳结果"——**状态机没有出口** |
| 每场景 6 条用例 | 验收门槛「≥90%」 | 6 条的分辨率是 16.7 个百分点，**90% 在单场景层面无法表达** |

**检查手法**：把所有数量约束（字段数、轮次、条数、并发、时限、容量）列成一张表，两两相乘验算。

**修复模式**：改变机制而非放宽数字。本例是"成组追问"替代"逐个追问"——一次抛出全部剩余必填项，前端本来就规划了表单形态，实现反而更省。

## 数据层

### A6 死字段

**识别**：字段存在，但没有任何查询或计算路径消费它。危险在于**它的存在被当作能力的证据**——尤其那些有行业质感、显得作者很懂业务的字段。

**实例**
| 字段 | 声称 | 实际 |
|---|---|---|
| `changeover_min`（换型损耗） | 支撑"延误判定具备真实计算逻辑" | `plan_start`/`plan_end` 是绝对时间，完工时刻已给定，延误判定只是两个日期比大小，该字段完全不参与运算 |
| `qty_locked`（库存预占） | — | 流程里没有任何一步写它 |
| `delta_e`（色差） | "跨缸判定依据" | 没有容差阈值字段可比对，且未说明相对哪个基准测量 |

**检查手法**：对每个"有行业质感"的字段，追一遍**它被哪个查询或计算读取**。读不到就是死字段。

**修复模式**：要么补齐使它承重的配套（本例是加产线产能表，使 ETA 推演成立），要么诚实地把它降级为展示字段并删掉相关能力声称。

---

### A20 单位缺失

**识别**：数量字段无计量单位列，而跨表比较时单位可能不同。

**实例**：订单行有 `uom`（米/平方米/件），库存批次和排产计划**都没有**。瓷砖按平方米下单、按片或箱入库、按片生产——订单说 500 平方米，库存说 800（片？箱？㎡？），库存校验在比不可比的数。

**检查手法**：所有数量字段检查是否有单位列；跨表比较的路径上，单位必须同源或有换算。

**修复模式**：PoC 阶段最省的做法是加 `uom` 列 + 在数据生成规则里**强制同一 (BU, 产品) 只用一个单位**，并写明"单位换算不在范围内"。两列加一行约束，成本≈0，但演示时数字带单位，对行业听众的可信度差别很大。

## 需求与验收层

### A7 指标无对象

**识别**：验收指标要测的东西在设计里根本不存在。

**实例**：测试集明列「越权查询」为边界用例，但全文**没有任何权限模型**——无用户表、无 user→BU/区域映射、无行级过滤、无检索侧身份过滤。更细一层：业务表连 `region` 字段都没有（它只存在于 RAG 元数据里），**区域级越权在当前 schema 下根本不可表达**。

这是文档的内部矛盾：要么补设计，要么删用例，不能两存。

**检查手法**：把测试集/验收指标与组件清单做**双向映射**。每条指标 → 它测的实现物；每个实现物 → 覆盖它的指标。两个方向的空缺都要解释。

---

### A8 指标无谓词

**识别**：指标有数字没有判定规则，因而不可证伪。

**实例**：「五个主线场景端到端成功率 ≥90%」——什么算"成功"？调对了 API、返回了对的数据、还是措辞也对？多轮澄清里第一问问偏但最终收敛算不算？全篇没有判定谓词。

**检查手法**：每个指标问三件事：**谁来判 / 按什么规则判 / 判错了怎么发现**。

**修复模式**：把"评分细则 + 标准答案 + 标准引用"作为**实现之前**的交付物，commit 进版本库，报告中注明冻结的 commit 号（预注册）。这防的是一个真实的心理效应：由同一人在**看到结果之后**拟定细则，标准会无意识地向观测结果对齐。

配套：把主观打分改成**二元判定**——「答案中每一条关键事实（数值、条款编号、期限、比例）都能在至少一条引用中逐字或语义等价地找到；有任一条找不到即计为不通过」。二元比 1–5 分打分稳定得多。

---

### A19 自评闭环

**识别**：同一人写题、答题、判卷，并写"我的方案是否可行"的结论。全部偏差同向。

**实例**：单人 PoC 的全部评测链条。叠加三重问题：样本量小（n=40，95% 置信区间约 76%–97%）、单次运行（无固定温度与种子，运行间方差与被比较的差异完全混淆，1 条 flake = 2.5 个百分点）、自评。

**检查手法**：把评测链条上每个环节的执行者列出来——出题、实现、运行、判卷、写结论。同一人占了几环？

**修复模式**（按性价比排序）：
1. **请需求方用自己的话出 10–15 条题**——开发者成本≈0，是效度问题最强的解药
2. 固定温度与随机种子并写进报告；核心档位各跑 3 次取多数（机器时间为主）
3. 引入第二判卷人（可以是 LLM-as-judge）并给出**人机一致率**
4. 每个数字标注 n 与置信区间

---

### A15 目标无落点

**识别**：立项目标在架构里找不到承接组件。到交付时该目标拿不出证据。

**实例**：立项四项待验证能力之一是「静态知识与动态业务数据的**融合**问答」。但五个子图里一个是纯检索、四个是纯 SQL；跨源联动分析也全是 SQL，没有知识文档参与。架构层面的请求分流甚至**把两者分开**了（纯知识问答直通知识库、业务查询走 Agent）。验收指标里也没有对应项。

**检查手法**：目标清单 × 组件清单**双向映射**，同 A7。

**修复模式**：不新增组件，在已有组件里加融合路径。本例：库存子图加「这批货 ΔE 2.3，能不能发给要求同缸的客户」（SQL 取色差值 + 检索判定阈值 + 合并作答）；政策子图加「这个客户这季度能拿几折」（SQL 汇总累计金额 + 检索阶梯条款 + 用金额匹配档位）。同时补上三个洞：融合有证据、纯检索场景不再单薄、两类证据可在同一 UI 卡片演示。

## 安全层

### A16 不可信输入与特权同域

**识别**：不可信文本与写能力（或其他敏感能力）共享同一个上下文。

**实例**：用户自然语言 + 检索到的文档内容都进入 LLM 上下文，而该 LLM 能调用创建订单的写 API。**最严重的是间接注入**——知识库按设计允许业务人员自助上传文档，等于**任何业务人员都可以往会进入 LLM 上下文的语料里写任意文本**。这不是理论攻击面，是设计写明的常规使用方式。

而"二次确认"防的是**模型犯错，不是模型被操纵**——被投毒文档产出的确认卡片在字段结构上完全合法，业务人员不会逐字符核对客户编码。

**检查手法**：画数据流，标注每段文本的**可信级别**和它能触达的**能力集合**。不可信文本与写能力的交集就是攻击面。同时盘点外泄通道：通知渠道、引用原文渲染、任何模型可触达的出站请求。

**修复模式**：最便宜且收益最大的一条是**架构不变量声明**——「写子图不摄入任何检索文本，写载荷只能来自对话槽位与用户确认过的卡片」。多数设计的拓扑已经几乎做到，把它写成约束即可基本关闭间接注入面。**这是利用现有架构而非增加架构。**

配套（各约一行）：确认令牌**绝不进入送往模型的上下文**（否则注入可诱导模型自我确认）；数据范围过滤器由**服务端按身份注入**，不接受模型或前端指定（否则它既不是权限控制也是注入靶点）；通知目标固定在配置里；引用原文纯文本渲染。

**测试集加 6–8 条注入用例——这应视为 PoC 的产出而非成本。**"让 LLM 持有写权限的注入风险有多大"正是规模化决策最需要的数据点。

## 环境层

### A9 核算漏项

**识别**：资源或工期核算表，与组件清单、任务清单对不上。

**实例二则**
| 核算 | 漏了 |
|---|---|
| 内存表：Dify 3.5 + PG 0.5 + 应用 0.5 + 前端 0.5 = 5GB | 部署拓扑里列了的 **Embedding/Rerank（2.5–4.5GB）**、Docker VM（1.0–1.5GB）、宿主 OS 与浏览器编辑器（实测已占 9.6GB）。重估中位 18.7GB，机器只有 16GB |
| 工期 36 人天 | **首次 GPU 部署（权重下载 + 显存调参）一天工都没计**，而它是 P1 验收信号的前提 |

**检查手法**：核算表与清单**逐项对照**。清单里有而表里没有的，逐个要求解释。

**为什么这条特别重要**：内存超限的后果不只是"卡"。统一内存进 swap 后，本地检索与重排的耗时会漂移，而**延迟指标与并发压测结论都在这台机器上测**——核心交付物的数据被污染。

---

### A10 默认配置陷阱

**识别**：处置方式基于对配置机制的错误理解。

**实例**：文档写「从 `COMPOSE_PROFILES` 中移除 `postgresql` 与 `pgvector` 两个条目」。但实际的默认值是**插值派生**的：

```
COMPOSE_PROFILES=${VECTOR_STORE:-weaviate},${DB_TYPE:-postgresql},collaboration
```

按要求设 `VECTOR_STORE=pgvector` 后，它会**自动重新包含 `pgvector`**，容器照起——想避免的多余实例原样出现。正确做法是**显式覆写为字面量**。

**检查手法**：凡涉及"改配置即可"的处置，去看该配置项的**实际定义方式**——是字面量、插值、还是从别处派生。

---

### A11 约束错位

**识别**：把约束用在它不成立的地方。

**实例**：「本机 16GB 内存扛不住多组件」这条约束，被用来否决一个**部署在另一台机器上**的组件选型。约束真实存在，但作用边界搞错了。

**检查手法**：每条约束标注它作用的**物理边界**（哪台机器、哪个进程、哪个网络域）。引用该约束时核对边界是否匹配。

## 交付层

### A17 交付倒置

**识别**：高风险、高工作量的产出集中在最后阶段，而该阶段同时承接前面所有阶段的延误。风险画像是倒置的。

**实例**：八份交付文档共 4.5 人天全部压在最后阶段，同阶段还要跑评测、做压测、写报告。

**检查手法**：把交付物按阶段画柱状图，看形状。末段高耸就是倒置。

**修复模式**：随阶段增量产出——部署运维文档在环境搭完时写、API 文档由 OpenAPI 生成、落地手册每阶段追加一节。几乎不增加总量，但把悬崖摊平，并让中间里程碑真正成为可交付兜底。

---

### A18 前置错风险

**识别**：前置了**有便宜退路**的风险，把**二元、无退路、补救手段全在上游**的风险留到最后。

**实例**：前置验证了数据库大版本兼容性（退路是改一行连接串换驱动），却把「≥85% 引用准确率是否可达」留到最后阶段才测量——而它的补救手段（重构文档结构、改元数据 schema、换切块策略）**全在上游**。

**检查手法**：每个风险标注两个属性——**失败后的补救成本**、**补救手段在哪个阶段**。按补救成本降序前置，而不是按"技术上有多不确定"排序。

**修复模式**：设立独立的前置验证期，把二元风险做成 spike。本例的 spike 是"拿最难的一份文档进知识库，问 5 个问题人工核对引用可溯源"——半天，但它决定整条检索路径是否要重做。

### A5-b 估算的自上而下嫌疑

**识别**（这是 A5 在工期上的变体，值得单列判据）：**看估算的修订史。如果每次变动都是"补记漏项"且只单向上调，那基数就是拍的。**

**实例**：工作量轨迹 30 → 31 → 31.5 → 36，每次变动都是发现遗漏。同时任务级 WBS 被列为**最后阶段**的交付物——本该用来做估算的工具，排在估算之后产出。

配套还有一个换算错误：「36 人天 ÷ 5 天/周 = 7.2 周」**把人天当成了日历工作日**，隐含 100% 投入效率。单人项目计入沟通、环境折腾、上下文切换后，现实通常是每周 3.5–4 个有效人天。

**修复模式**：把 WBS 前移做估算工具；按有效人天换算；缓冲**集中持有**不预先摊进各阶段（均匀铺开的缓冲对集中在某两阶段的方差无效），并设**日历决策门**——到点未达进度即由决策者启用砍范围清单，不由实施者临场决定。

## 文档演化层

### A12 派生决策未重算

**识别**：上游决策变了，依赖它的下游决策没跟着重算。

**实例**：「GPU 改用按小时计费的租用实例」这个变更，连带使「权威数据库放 GPU 服务器」不再成立——可随时释放的实例不能承载业务数据、审计日志与向量索引。但该决策留在原处，直到评审才发现。

**检查手法**：每次改动后，全文搜索**被改决策的名字**，检查所有提及处是否仍然成立。

---

### A13 论据部分推翻即换结论

**识别**：一个由多条理由支撑的结论，推翻其中一条就改换方案，不重审其余。

**实例**：向量库选型原有四条理由，发现其中一条（内存约束）用错了地方（见 A11），随即改选另一方案；但剩下三条理由（少一个组件、运维体系统一、SQL 可对账）在项目规模下仍然成立。一轮之后又改回来。

**检查手法**：结论变更时，把原理由**逐条重新评估并把评估结果记录进修订说明**。只推翻了一条，其余成立，则结论不变。

---

### A14 基准自相矛盾

**识别**：用作核对基准的文档（宪法、规范、契约）与主文档矛盾。以它为基准的检查机制随即空转——按哪份查都能得出相反结论。

**实例**：宪法条文写「该接口**不声明写方法**」，而设计文档的接口定义里有 `upsert` / `delete_by_doc` / `create_collection` / `drop_collection` / `switch_alias` 五个写方法。而收敛检查正是以宪法为基准。

**更根本的问题**：该基准文档在**一行代码都没写、文档总量仅 1200 行时**，就已落后主文档三个版本——它正是为对抗漂移而设的机制。

**检查手法**：基准文档与主文档做**交叉一致性检查**；基准的版本引用必须与主文档同步；把"基准与主文档版本一致"列为每次收敛检查的**第一项**。

**修复模式**：基准条文的"如何验证"要写成**可机械执行**的一句话（例如"仓库里 grep 不到写方法"），而不是需要人判断的描述。可机械执行的条文才能进 CI，进了 CI 才不会漂移。
